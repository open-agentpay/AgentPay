# x402 是什么？用 HTTP 402 实现程序化支付

## 一、先理解 HTTP 402

你每天访问网站时，浏览器和服务器通常通过 HTTP 协议进行通信。

常见的 HTTP 状态码包括：

- `200 OK`：请求成功。
- `400 Bad Request`：请求格式或参数有问题。
- `401 Unauthorized`：缺少有效认证。
- `403 Forbidden`：服务器拒绝访问。
- `404 Not Found`：资源不存在。
- `500 Internal Server Error`：服务器发生错误。

HTTP 还定义了 `402 Payment Required`，即“需要付款”。

这个状态码很早就出现在 HTTP 标准中，但长期以来并没有形成广泛统一的通用支付交互方式。

x402 则尝试利用 HTTP 402 及相关协议约定，让网站或 API 可以向程序化客户端提出支付要求。

## 二、x402 是什么？

x402 是一种面向互联网资源付费访问的开放支付协议体系。

它的一个典型思路是：

> 客户端请求资源，服务端声明需要付款；客户端根据支付要求完成授权和支付流程，再次请求资源。

例如，一个 API 服务商希望对每次数据查询收取 0.01 USDC。

传统方式可能要求用户：

1. 注册账号。
2. 创建 API Key。
3. 绑定支付方式。
4. 购买套餐。
5. 调用 API。

对于一些需要频繁、自动调用不同服务的 Agent，这种流程可能比较繁琐。

采用 x402 的服务可以在资源请求过程中返回支付要求，让支持相应协议的客户端按照约定完成支付流程。

需要注意，x402 并不意味着所有 HTTP API 都会自动支持支付。服务端和客户端仍然需要实现兼容的协议流程。

## 三、x402 的基本工作流程

假设一个数据 API 的收费标准为每次 0.01 USDC。

客户端第一次请求：

```http
GET /v1/market-data HTTP/1.1
Host: data.example.com
```

服务端发现当前请求不满足付费访问条件，返回类似这样的响应：

```http
HTTP/1.1 402 Payment Required
Content-Type: application/json
```

响应正文会按照所采用的 x402 版本和具体支付方案，描述所需支付的信息。

可以把它理解为：

```json
{
  "resource": "/v1/market-data",
  "price": "0.01",
  "asset": "USDC",
  "network": "example-network"
}
```

**注意：以上 JSON 只是教学示意，不是可直接使用的 x402 V2 标准报文。** 实际字段、编码方式、支付要求和请求头应以对应版本的官方规范与 SDK 为准。

客户端收到 402 后，需要检查支付要求是否符合预期，然后决定是否继续。

如果允许支付，客户端按照所使用的支付方案生成授权或支付凭证，再次请求资源。

```text
客户端请求资源
       ↓
服务端返回 402
       ↓
客户端解析支付要求
       ↓
检查价格、网络、资产和策略
       ↓
生成支付凭证
       ↓
携带支付信息重新请求
       ↓
服务端验证支付信息
       ↓
交付资源
```

服务端具体如何验证支付、何时结算，取决于协议版本、支付方案和服务端实现。

## 四、x402 与 AgentPay 是什么关系？

可以将它们理解为不同层次的能力。

### x402：支付交互协议

主要解决客户端和付费服务之间如何表达支付要求、提交支付信息，以及完成约定的支付交互。

### AgentPay：支付控制层

主要关注：

- Agent 是否有权购买该服务。
- 价格是否超过单笔限额。
- 预算是否充足。
- 服务商是否在允许名单中。
- 是否出现异常调用频率。
- 支付失败或状态未知时如何恢复。

架构可以表示为：

```text
AI Agent
    ↓
AgentPay Buyer SDK
    ↓
支付策略与预算控制
    ↓
x402 交互
    ↓
服务端 / Facilitator
    ↓
支付结算
```

这里的 AgentPay Buyer SDK 是 AgentPay 规划中的客户端组件，不代表所有模块已经完成。

关键区别是：

**x402 负责支付交互，AgentPay 负责控制 Agent 能否以及如何发起支付。**

协议不会自动替 Agent 决定合理的消费预算，也不会自动建立符合业务要求的资金安全策略。

## 五、什么是 Facilitator？

在某些 x402 支付方案中，Facilitator 是协助服务端处理支付验证与结算的组件。

可以将其理解为支付流程中的一个服务角色。

常见职责包括：

- 验证支付凭证是否符合要求。
- 检查签名或授权。
- 在支持的支付方案中提交或协调链上结算。
- 返回验证或结算相关结果。

实际职责取决于具体协议版本和实现。

一种简化架构是：

```text
Buyer
  ↓
Paid API
  ↓
Facilitator
  ↓
区块链网络
```

Buyer 负责发起请求，Paid API 负责控制资源访问，Facilitator 负责协议支持的验证与结算工作。

Facilitator 并不天然等同于托管钱包，也不能仅凭它返回成功，就忽略对最终链上状态的核验。

## 六、为什么 x402 适合探索 Agent 支付？

### 1. 交互可以由程序完成

客户端能够根据服务端返回的支付要求，执行相应的支付流程，而不一定需要用户逐次手动点击付款。

### 2. 可以支持按请求付费的服务

对于适合按量收费的 API，可以根据请求对应的资源或服务设置支付要求。

### 3. 可以与 Agent 工具调用结合

例如，Agent 需要调用一个付费数据工具：

```text
Agent
  ↓
调用 data.search
  ↓
服务返回支付要求
  ↓
AgentPay 检查策略
  ↓
允许支付
  ↓
客户端完成协议交互
  ↓
获得查询结果
```

这种方式可以让付费服务成为 Agent 工作流中的一个环节。

但前提是相关工具、支付客户端和服务端都实现了兼容的协议与业务逻辑。

## 七、x402 不负责解决哪些问题？

x402 不应该被理解为完整的 Agent 金融安全系统。

它本身并不替你完成所有以下工作：

- 设计 Agent 的每日预算。
- 限制 Agent 每分钟最多消费多少次。
- 判断服务商是否值得信任。
- 防止 Agent 陷入无限调用循环。
- 管理整个应用的支付状态。
- 保证上游服务一定能够交付。
- 自动处理所有重复扣款与恢复场景。

这些问题需要应用、支付控制层和底层支付实现共同解决。

## 八、AgentPay MVP 应该怎样使用 x402？

结合项目研发计划，合理的实现路径是：

1. 调研 x402 V2 规范和官方 SDK。
2. 明确哪些协议能力直接复用，哪些需要自行封装。
3. 实现支付要求的解析与编码。
4. 在买方客户端中接入策略校验。
5. 实现授权签名与请求重试。
6. 使用 Mock Facilitator 完成端到端测试。
7. 再逐步接入本地测试链和真实测试结算。

其中，Mock 测试只能证明应用内部流程符合预期，不能证明真实链上支付已经成功。

## 九、小结

x402 的核心思路是把付费访问融入程序化的 HTTP 交互流程。

可以记住这三个概念：

- **HTTP 402**：服务端表达需要付款。
- **x402**：围绕付费访问建立的协议交互方式。
- **AgentPay**：在 Agent 发起支付之前，增加策略、预算、风险控制和恢复能力。

对于 AgentPay，x402 是支付协议层，而不是整个产品的全部。
