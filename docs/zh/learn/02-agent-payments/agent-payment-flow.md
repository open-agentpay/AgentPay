# Agent 支付的完整流程

## 一、先看一个真实感更强的场景

假设用户要求：

> 帮我查询某个行业的市场数据，并整理成报告。

Agent 发现一个数据 API 可以提供所需信息，每次查询收费 0.01 USDC。

如果这个 Agent 接入了支付系统，它就可能在符合授权条件时自动购买数据。

但完整的支付流程远不止“发送一笔交易”。

它至少涉及：

1. 发起资源请求。
2. 接收服务端的支付要求。
3. 检查支付策略。
4. 预留预算。
5. 生成支付授权。
6. 验证支付信息。
7. 交付资源。
8. 完成结算。
9. 更新状态并处理异常。

不同协议和服务实现的具体顺序可能有所不同，下面以 AgentPay 规划中的 x402 买方、网关和 Facilitator 架构为例。

## 二、完整流程总览

```text
Agent
  ↓
Buyer SDK
  ↓
请求付费 API
  ↓
API / Gateway 返回 402
  ↓
解析支付要求
  ↓
Policy Engine 检查
  ↓
预算原子预留
  ↓
生成支付授权
  ↓
携带支付信息重新请求
  ↓
Gateway 验证支付信息
  ↓
调用上游服务
  ↓
交付资源
  ↓
执行或跟踪结算
  ↓
更新状态并对账
```

这里的核心是把支付授权、服务交付和结算视为相互关联、但不完全等价的过程。

## 三、第一步：请求资源

Agent 首先像普通 HTTP 客户端一样请求目标 API。

例如：

```http
GET /v1/market-data
Host: api.example.com
```

此时 Agent 不一定知道这个资源是否需要付款。

服务端可能直接返回资源，也可能返回支付要求。

## 四、第二步：服务端返回支付要求

假设 API 需要收费，服务端返回 HTTP 402。

客户端需要解析支付要求，并检查它是否符合自己的策略。

例如：

```text
服务：market-data
价格：0.01 USDC
网络：指定的测试网络
收款方：预先配置的服务商
```

这些是示意信息，不是标准协议报文。

客户端不应该盲目接受服务端提出的任何付款要求。

例如，如果用户只授权使用指定网络和白名单服务商，那么支付要求不符合条件时就应拒绝。

## 五、第三步：Policy Engine 评估

AgentPay 的策略引擎在这里发挥作用。

假设配置如下：

```yaml
policy:
  max_transaction_amount: 0.10
  daily_budget: 2.00
  allowed_merchants:
    - market-data
```

示例金额以 USDC 为单位，具体配置格式和语义需要在实际系统中定义。

支付请求为：

```text
商户：market-data
金额：0.01 USDC
```

系统检查：

```text
商户是否允许？          是
金额是否超过单笔限额？  否
每日预算是否充足？      是
调用频率是否正常？      是
```

如果全部通过，支付请求可以进入下一阶段。

如果商户不在允许名单中，即使价格很低，也应该拒绝。

**策略引擎不是模型给出的建议，而是实际执行前必须通过的程序检查。**

## 六、第四步：原子预留预算

为什么不能只检查预算？

假设剩余预算为 0.05 USDC，同时有两个请求，每个请求需要 0.04 USDC。

如果两个请求同时检查剩余预算，都可能认为预算充足。

因此，系统需要将检查与预算预留结合起来。

```text
剩余预算：0.05
      ↓
请求 A 预留 0.04
      ↓
剩余可用预算：0.01
      ↓
请求 B 申请 0.04
      ↓
预算不足，拒绝
```

预算预留不是最终扣款，而是暂时为该请求占用预算空间。

后续根据执行结果，系统可以提交消耗或释放预留。

对于 AgentPay 的 MVP，预算预留需要依托 SQLite 事务等机制实现并发安全。

## 七、第五步：生成支付授权

预算通过后，客户端还需要按照所使用的支付方案生成相应的授权信息。

在某些 EVM 支付方案中，这可能涉及 EIP-712 结构化数据签名，以及 EIP-3009 相关授权。

大致过程是：

```text
支付要求
   ↓
验证网络、资产、收款方和金额
   ↓
构建授权数据
   ↓
钱包或 Signer 签名
   ↓
生成支付凭证
```

这里需要特别强调：

签名不是支付策略本身。

签名表示某个密钥对特定数据作出了密码学授权，但它不能替代预算检查、商户限制和业务规则。

签名前应验证授权内容是否与原始支付要求一致。

## 八、第六步：提交支付请求

客户端将支付信息按照协议要求发送给付费服务。

服务端或相关支付组件需要验证支付信息是否有效。

验证可能涉及：

- 签名是否合法。
- 授权是否符合协议要求。
- 资产和网络是否匹配。
- 金额与收款方是否正确。
- 授权是否仍然有效。
- 是否已经被使用或处理。

具体检查项取决于所使用的支付方案。

不能仅凭客户端声称“我已经付款”，就认为支付已经得到验证。

## 九、第七步：交付资源

支付要求满足后，服务端按照其实现规则提供资源。

例如：

```text
通过支付验证
      ↓
调用上游数据 API
      ↓
获取市场数据
      ↓
返回 HTTP 200
      ↓
Agent 继续处理
```

但这里仍然可能出现上游故障。

例如：

```text
支付验证成功
      ↓
上游 API 超时
      ↓
没有返回数据
```

这时，系统应该记录交付失败或需要恢复的状态，而不是简单地让 Agent 从头开始付款。

## 十、第八步：完成或跟踪结算

某些支付方案中，支付授权验证、资源交付和链上结算并不是一个同步完成的动作。

例如，Facilitator 可能在资源交付之后执行结算。

因此，需要分别跟踪：

- 支付请求是否被授权。
- 服务是否已经交付。
- 结算是否已经提交。
- 链上交易是否已经确认。

如果采用其他 x402 支付方案，具体的执行顺序可能不同，应按照对应协议和服务端实现处理。

## 十一、第九步：更新状态与处理异常

假设客户端提交结算请求后发生网络超时。

系统不能直接认定支付失败。

更合理的处理方式是：

```text
结算请求超时
      ↓
标记结果未知
      ↓
查询原请求或链上状态
      ↓
确认已成功？
  ┌───┴───┐
  是      否或仍未知
  ↓          ↓
更新状态   进入恢复流程
```

对于无法立即确认的结果，应保留状态并继续核验，而不是直接发起一笔全新的支付。

## 十二、AgentPay 为什么需要三类状态？

AgentPay 的设计将支付意图、结算和服务交付分别管理。

### Payment Intent：支付意图

记录用户或 Agent 想要执行的支付请求，以及该请求的授权与处理进度。

### Settlement：结算

记录支付是否已提交、是否已确认，以及结果是否未知。

### Fulfillment：服务交付

记录资源是否已经交付、是否失败，以及是否需要恢复。

这样可以表示复杂情况：

```text
Payment Intent：已授权
Settlement：已确认
Fulfillment：失败，需要恢复
```

如果只有一个简单的 `SUCCESS / FAILED` 字段，就很难准确表达这些状态。

## 十三、失败场景示例

假设 Agent 需要购买 0.01 USDC 的数据。

### 场景 A：策略拒绝

原因：服务商不在白名单中。

处理：拒绝请求，不进入签名和支付执行阶段。

### 场景 B：预算预留失败

原因：剩余预算不足。

处理：拒绝请求，不允许并发请求突破预算。

### 场景 C：支付结果未知

原因：请求超时，但无法确认服务端是否已处理。

处理：查询原请求状态，不直接创建新的支付请求。

### 场景 D：支付完成但交付失败

原因：上游 API 返回错误。

处理：保留支付记录，进入交付恢复流程，并避免重复扣款。

## 十四、小结

完整的 Agent 支付流程，不只是“请求 → 签名 → 付款”。

还需要考虑：

- 支付要求是否可信。
- 请求是否满足消费策略。
- 预算是否可以原子预留。
- 授权签名是否正确。
- 资源是否成功交付。
- 结算是否真正完成。
- 异常发生后是否能够安全恢复。

这些步骤共同决定了 Agent 支付系统是否真正可靠。
