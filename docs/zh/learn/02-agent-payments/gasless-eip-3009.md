# 钱包与支付签名：EIP-712、EIP-3009

## 一、为什么 Agent 支付需要签名？

在区块链上，系统需要判断一项操作是否得到了相应账户的授权。

例如，Agent 想使用某个地址中的 USDC 支付数据服务费用。

系统不能仅凭 Agent 发送一句：

> 我已获得用户授权，请扣除 0.10 USDC。

就相信这笔操作是合法的。

在 EVM 生态中，常见的授权方式涉及私钥、公钥、地址、数字签名和智能合约验证。

数字签名可以帮助验证：某份特定数据是否获得了对应密钥的授权，以及数据在签名后是否被修改。

但签名本身不等于完整的业务安全检查。

## 二、私钥、地址和签名是什么关系？

可以先用一个简化模型理解。

### 1. 私钥

私钥是用于生成签名的重要秘密信息。

谁能够使用私钥，就可能获得相应的签名能力。

因此，私钥不能随意暴露给模型、日志或不可信工具。

### 2. 地址

在常见的 EVM 账户体系中，地址与公钥及相关密码学过程有关。

地址通常用于标识账户或收款方，但仅知道一个地址，并不能证明它属于可信服务商。

### 3. 数字签名

签名是针对特定数据生成的密码学结果。

验证方可以检查签名是否与预期的签名者和数据相匹配。

例如：

```text
支付授权数据
      ↓
钱包或 Signer 使用私钥签名
      ↓
生成数字签名
      ↓
验证方检查签名与授权内容
```

**签名只证明相应的密码学授权关系，不代表这笔交易已经结算成功。**

## 三、为什么不应该让 Agent 直接持有私钥？

假设 Agent 可以直接读取用户钱包的私钥。

一旦出现以下情况：

- 模型产生错误决策。
- 工具受到提示词注入影响。
- 程序陷入循环。
- 恶意代码获得执行权限。

攻击者或错误程序就可能滥用签名能力。

更合理的架构是：

```text
Agent
  ↓
支付请求
  ↓
Policy Engine
  ↓
权限与预算检查
  ↓
Signer
  ↓
生成授权签名
```

Signer 负责执行密码学操作，Policy Engine 负责判断请求是否满足支付规则。

两者职责不同。

在 MVP 的本地测试环境中，可以使用专门的测试私钥实现签名；生产环境则需要根据风险和部署方式设计密钥隔离方案。

## 四、EIP-712 是什么？

EIP-712 是以太坊生态中用于结构化数据哈希和签名的标准。

它的一个重要价值是，让签名内容具备明确的结构，而不是只对一段难以理解的原始文本进行签名。

例如，一份支付授权可能包含：

```text
付款方
收款方
资产
金额
有效期
授权标识
```

这里仅是概念示例，并非特定合约的标准数据结构。

通过结构化签名，签名者和验证方可以围绕明确的数据字段进行处理。

但这并不意味着用户一定能够直观理解所有字段，也不意味着所有签名请求都是安全的。

程序仍然需要检查：

- 目标网络是否正确。
- 合约地址是否可信。
- 资产是否符合预期。
- 收款方和金额是否符合策略。
- 签名域与业务上下文是否正确。

## 五、EIP-3009 是什么？

EIP-3009 描述了一类基于签名授权的代币转移机制。

对于支持相应接口的代币，授权方可以对一笔代币转移进行签名授权，由符合合约规则的调用方提交授权并执行转移。

这类机制可以支持由其他参与方提交交易的支付设计。

例如：

```text
Agent
  ↓
生成代币转移授权
  ↓
使用授权方密钥签名
  ↓
提交授权
  ↓
符合条件的调用方提交交易
  ↓
代币合约验证并执行转移
```

具体行为取决于代币合约实现、授权类型和有效性检查。

**不是所有 ERC-20 代币都支持 EIP-3009。** 使用前必须确认目标代币合约确实实现了所需接口。

## 六、EIP-712 与 EIP-3009 有什么区别？

两者不是同一层面的标准。

| 对比 | EIP-712 | EIP-3009 |
|---|---|---|
| 主要用途 | 定义结构化数据的哈希与签名方式 | 定义特定的基于签名授权的代币转移机制 |
| 关注点 | 签名数据如何表达和验证 | 代币转移授权如何执行 |
| 是否等于支付协议 | 否 | 否 |
| 是否要求所有代币支持 | 不适用 | 需要目标合约实现相应接口 |
| 在支付系统中的位置 | 可以作为签名机制的一部分 | 可以作为特定代币支付方案的一部分 |

在一些支付实现中，两者可能配合使用，但不能简单认为任何 EIP-712 签名都能执行 EIP-3009 转账。

## 七、为什么这种方式可能适合微支付？

传统链上交易通常需要有人提交交易并支付相应网络费用。

对于频繁、金额较小的 API 支付，如果每次都要求 Agent 自己准备原生 Gas Token，就会增加使用复杂度。

在支持相应授权机制的方案中，可以将授权签名与实际交易提交分开。

例如：

```text
Agent
  ↓
签署代币转移授权
  ↓
Facilitator 提交交易
  ↓
支付执行
```

在符合协议和代币合约条件的情况下，Agent 不一定需要为每次支付自行提交链上交易。

不过，这不意味着交易没有 Gas 成本。

链上交易仍然需要支付网络费用，只是费用由谁承担、如何结算，需要根据具体架构确定。

## 八、签名授权并不能替代支付策略

假设 Agent 获得了一份合法签名，可以转移 100 USDC。

即使签名有效，也不代表该笔支付一定符合用户为 Agent 设置的预算规则。

例如，用户只允许 Agent 每笔最多消费 1 USDC。

如果系统只验证签名是否有效，却不检查授权内容是否符合预算和商户限制，就可能违反业务规则。

因此，正确的逻辑应该是：

```text
解析支付要求
      ↓
验证业务规则
      ↓
检查预算和权限
      ↓
核对签名内容
      ↓
提交授权
      ↓
跟踪执行与结算状态
```

还应根据底层合约和支付方案，检查授权的有效期、唯一标识以及防止重复使用的机制。

## 九、EIP-3009 授权是否可以无限使用？

不能仅凭“使用了 EIP-3009”就认为授权一定是无限的或一定是一次性的。

具体授权范围取决于签名中包含的数据和目标合约的验证规则。

在设计支付客户端时，需要确认：

- 授权金额。
- 收款地址。
- 资产与合约。
- 网络与签名域。
- 授权有效期。
- 防重放或唯一性机制。
- 授权是否已经使用。

这些检查应与 AgentPay 的策略引擎结合，确保签名内容与已批准的支付请求一致。

## 十、AgentPay MVP 中如何处理签名？

结合当前研发计划，适合先采用分层实现。

### 第一层：Signer 接口

统一签名能力的调用方式。

```text
Policy Engine
      ↓
Signer Interface
      ↓
LocalSigner
```

本地签名器适合开发与测试，不应被直接视为生产密钥管理方案。

### 第二层：授权数据构建

将经过策略批准的支付请求转换为具体支付方案要求的数据结构。

### 第三层：签名与验证测试

测试正确签名、错误签名、错误网络、错误金额和过期授权等情况。

### 第四层：测试链结算

在本地测试链中验证授权提交、合约执行和最终状态核验。

只有测试结果能够证明完整流程正确，才能说相应测试链链路已经打通。

## 十一、小结

理解 Agent 支付签名，需要区分三个层次：

- **EIP-712**：结构化数据的哈希与签名标准。
- **EIP-3009**：特定的基于签名授权的代币转移机制。
- **AgentPay Policy Engine**：判断 Agent 是否有权执行某笔支付的业务控制层。

签名可以证明授权，但不能替代预算、权限、风险和状态管理。

最终目标不是让 Agent 拥有更大的密钥控制权，而是让它能够在明确授权和严格规则下完成支付。
