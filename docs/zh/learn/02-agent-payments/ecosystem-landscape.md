# 其他 Agent 支付方案的中立介绍

> **一句话**：Agent 支付是一个快速演进的领域，多个协议并存，且**解决的是不同层面的问题**，并非简单的"谁取代谁"。
>
> ⚠️ **时效声明**：本篇内容**核对于 2026-10-21**。该领域变化很快，名称、归属、状态可能已有变化，使用前请以各项目官方文档为准。本篇力求中立，只描述定位，不做优劣评判。

**本篇你会了解**：主要协议/方案各自解决什么问题、处在技术栈的哪一层、在实际场景中如何协同工作，以及它们与 AgentPay 的边界关系。

---

## 1. 先建立一个分类框架：不要把苹果和梨放在一起比

面对层出不穷的新名词（x402、AP2、ACP、UCP、MCP……），初学者最容易陷入的误区是把所有方案放进同一张"谁更好、谁会干掉谁"的表格里。

实际上，一次完整的商业行为包含**连接工具、挑选商品、证明用户授权、风控审批、资金划转**等多个环节。更有用的问法是：**它解决的是哪个层面的问题？**

| 层面 | 核心回答的问题 | 典型场景举例 | 代表方案 |
|---|---|---|---|
| **工具/通信协议** | Agent 怎么调用工具、与其他 Agent 协作？ | Agent 发现并调用外部天气查询或翻译接口 | MCP、A2A |
| **电商交易协议** | Agent 怎么发现商品、加购、下单、结账？ | 帮用户在电商平台挑选一双跑鞋并填写收货地址完成下单 | ACP、UCP |
| **授权与信任协议** | 如何向商户/银行证明"真的是人类用户授权了这笔交易"？ | 发生盗刷争议时，商户出示密码学证据证明用户确实下达过采购指令 | AP2、Visa TAP、Mastercard Agent Pay |
| **★ 金融控制层** | Agent **该不该**付、最多付多少、超时失败了怎么办？ | 拦截因幻觉导致的 $500 异常扣款、防止死循环高频刷爆日预算 | **AgentPay 定位于此**（见第 4 节） |
| **支付/交付协议** | 怎么在 HTTP 请求/机器通信里完成具体的付款动作？ | 调用 API 返回 `402`，客户端附带签名凭证完成 `0.01 USDC` 结算 | x402、Stripe MPP |

## 2. 主要方案一览与实例解析

> 以下为截至 2026 年 10 月公开信息的概括，技术细节请以各项目最新官方文档为准。

### 2.1 机器支付与交付层：x402 与 Stripe MPP

#### x402（HTTP 402 稳定币支付协议）
- **定位**：基于原生 HTTP `402 Payment Required` 状态码的开放支付协议，主要用于稳定币的按请求微支付（Pay-per-request）。
- **演进与治理**：由 Coinbase 于 2025 年 5 月推出，V2 版本于 2025 年 12 月发布；2026 年 4 月起移交由 Linux Foundation 旗下的 **x402 Foundation** 中立治理，并于同年 7 月完成运营启动，成员涵盖多家支付巨头、云厂商与加密基础设施公司。
- **生态特点**：协议本身与具体区块链网络无关（支持 Base、Arbitrum、Solana 等多条链），且生态中存在多个中继结算方（Facilitator）实现（如 Coinbase CDP、Cloudflare 等）。
- **与 AgentPay 的关系**：AgentPay 的链上轨**原生实现并使用** x402 V2 协议。打个比方：**x402 是连接买卖双方的“支付高速公路”，而 AgentPay 是装在买方车上的“智能刹车与油耗控制系统”**——二者是"底层通信协议"与"上层控制层"的互补关系。

#### Stripe Machine Payments Protocol（MPP）
- **定位**：支付巨头 Stripe 面向机器间支付（M2M Payments）推出的协议方案，同样支持稳定币结算（据公开资料由 Stripe 与 Tempo 共同推动）。
- **说明**：它与 x402 属于针对同一类"机器对机器自动支付"问题的不同技术路线。二者在生态绑定、治理模式与开放程度上各有特点，具体差异请查阅各自官方规范。

### 2.2 授权与卡网络信任层：AP2 与卡组织方案

当 Agent 代替人类去消费时，商家和银行面临一个巨大的法律与合规难题：**如果事后人类用户拒付（Chargeback），声称“是 AI 自己乱买的，我没同意”，谁来背锅？** 这一层的协议正是为了解决这个“授权证明”问题。

#### AP2（Agent Payments Protocol）
- **定位**：解决**授权与问责（Authorization & Accountability）**——通过密码学可验证的"数字授权书（Mandate）"，证明人类用户确实在特定边界内授权了某笔交易。
- **演进与要点**：由 Google 于 2025 年 9 月发起，核心机制是使用 `Intent Mandate`（意图授权）、`Cart Mandate`（购物车授权）、`Payment Mandate`（支付授权）等逐级签名的结构化对象。它与底层支付方式无关（信用卡、银行转账、稳定币皆可承载）。据公开报道，2026 年 4 月 Google 已将其捐赠给 **FIDO Alliance** 进行行业中立治理；其稳定币结算分支亦可借助 x402 作为底层扩展。
- **通俗例子**：
  > 用户对手机助手说：“帮我盯一下旧金山飞东京的机票，低于 $800 就直接买。”
  > 用户用手机指纹（Passkey / FIDO）签下一份 `Intent Mandate`（包含上限 $800、航线等条件）。当三天后 Agent 发现 $750 的机票并自动下单时，会将这份带有用户硬件签名的 Mandate 出示给航司和支付网关，作为“用户本人真实授权”的铁证。
- **与 AgentPay 的关系**：关注点处在不同阶段——**AP2 偏重"向外部证明人类用户的授权合法性"，而 AgentPay 偏重"在已获授权的预算池内，对成百上千次高频 API 调用进行实时余额预留、并发锁控与网络超时故障恢复"**。

#### 卡组织方案：Visa TAP / Intelligent Commerce、Mastercard Agent Pay
- **定位**：把 AI Agent 安全地纳入**现有的全球信用卡/借记卡清算网络**。
- **核心机制**：不替代现有的刷卡网络，而是在其上叠加"Agent 可信身份注册 + 专用动态令牌化（Tokenization） + 发卡行风控信号"。
- **通俗例子**：你不需要把真实的 16 位信用卡号和 CVV 明文塞进 Agent 的 Prompt 里（那样极易泄露），而是由 Visa/Mastercard 为你的 Agent 签发一张虚拟的“受限受控子卡 Token”（例如限定只能在某几个商户消费、单笔最高 $50），让传统商户无需改造收银台就能接收 Agent 的刷卡消费。

### 2.3 电商交易流程层：ACP 与 UCP

买 API 数据只需一次 HTTP 调用，但买实物商品涉及“搜索商品 → 选尺码规格 → 算运费税费 → 填地址 → 结账 → 售后退换”。这就是电商交易协议要标准化的领域。

#### ACP（Agentic Commerce Protocol，OpenAI × Stripe）
- **定位**：面向**对话界面内的购物与结账（In-chat Checkout）**，让 Agent 在不向商户直接暴露买家敏感支付凭据的情况下，丝滑完成商品下单（底层借助 Stripe 的共享支付令牌 Shared Payment Token 等机制）。
- **⚠️ 重要同名区分**：Web3 与加密业界另有一个同样缩写为 **ACP** 的项目——即 **Virtuals Protocol 推出的 Agent Commerce Protocol**（主要用于多 Agent 之间的任务外包撮合、工作成果验证与链上智能合约托管结算 / Escrow，并关联 ERC-8183 等标准）。**这两者虽然都叫 ACP，但发起方与业务场景完全无关，阅读资料时务必注意区分。**

#### UCP（Universal Commerce Protocol）
- **定位**：覆盖商品发现、购物车管理、结账、订单追踪与售后服务的全链路电商流程标准，主要由 Google 与零售生态伙伴共同推动。它聚焦于**标准化的商品交易业务流**，而非最底层的资金划转技术。

### 2.4 平台级、区域性方案与非支付互补协议

#### 平台与区域性生态方案
- **Cloudflare**：在其 Workers 与 Agents SDK 中深度集成了 x402 协议，为开发者提供开箱即用的“按请求付费”边缘网关能力；
- **Coinbase**：提供 AgentKit、MPC 托管/非托管 Agent 钱包以及付费 API 服务目录（Bazaar）等全套工具链；
- **Alipay（支付宝）AI Pay 等**：面向中国本土合规市场的智能体支付解决方案，针对国内小程序、生活服务与大模型生态，推出了面向 AI 智能体的专属收付款与账单管控产品。

#### 互补的非支付协议：MCP 与 A2A
- **MCP（Model Context Protocol）**：定义了大模型与外部工具/数据源交互的标准接口（回答"Agent 如何规范地调用工具"）；
- **A2A（Agent-to-Agent Protocol）**：定义了不同厂商、不同架构的 Agent 之间如何发现彼此、派发任务与同步协作状态。
- **协同逻辑**：MCP 和 A2A 本身并不处理资金划转，但当一个 MCP 工具是“付费工具”、或一个远端 A2A Agent 是“收费专家”时，它们提供了标准的**业务调用通道**，并在通道内挂载 x402 等协议的支付凭证来完成闭环。

### 3.2 实战推演：多个协议如何在一次任务中叠加协作？

为了证明这些协议是**“叠加协作”而非“彼此互斥”**，我们来看一个假想的端到端企业级场景：

> **场景：分析师让 AI Agent 撰写一份深度行业研报，并给定了 $5 的总预算**
> 1. **人类授权（AP2 层）**：分析师下达任务，签发一份上限为 `5 USDC` 的授权凭证（Mandate），赋予该调研 Agent 消费权限。
> 2. **工具调用（MCP 层）**：Agent 通过 **MCP 协议** 连接到了外部的一个“付费金融研报数据库 MCP Server”，请求拉取某公司的财报数据。
> 3. **触发收费挑战（x402 层）**：该数据源要求付费 `0.2 USDC`，于是通过底层 HTTP/MCP 通道返回 **x402** 的支付挑战（包含收款地址、金额、Base 链 ID）。
> 4. **实时风控与签名（AgentPay 金融控制层）**：
     >    - Agent 的请求经过 **AgentPay 网关**；
>    - AgentPay 校验身份、核对目标域名白名单、检查滑动窗口预算（$5 剩余充足）、检测未处于死循环高频调用；
>    - AgentPay 在本地数据库**原子冻结** `0.2 USDC` 额度，并生成幂等键，随后调用隔离的签名器生成 EIP-3009 离线授权签名。
> 5. **链上清算与交付（Facilitator + 区块链层）**：携带签名的请求重发给数据源，数据源通过 Facilitator 在 Base 链上完成结算，确认无误后将财报数据通过 MCP 返回给 Agent。

在这个例子里，**MCP 负责“怎么调工具”，AP2 负责“人类授没授权”，x402 负责“怎么传递付款支票”，而 AgentPay 守在最关键的资金出口处，负责“每一分钱花出去前的毫秒级风控、并发锁控与异常兜底”**。

## 4. AgentPay 的清晰定位与边界（Do's & Don'ts）

为了保持架构的纯粹性与高可靠性，AgentPay 明确划定了自己的能力边界：

### AgentPay 做什么（核心职责）：
在 AI Agent 运行时与真实资金（链上私钥或平台余额）之间，提供一层**独立于 LLM 的确定性金融控制层（Financial Firewall & Control Plane）**：
- 细粒度策略引擎与滑动窗口预算控制；
- 数据库级原子预算预留（防并发超支）；
- 高频死循环检测与秒级熔断（Kill Switch）；
- 三态解耦状态机（Intent / Settlement / Fulfillment）与网络超时幂等恢复；
- 多租户身份强解析与只追加（Append-Only）可观测审计账本。

### AgentPay 明确不做什么（非目标 / Non-Goals）：
- ❌ **不重复造轮子发明新的支付传输协议**：链上轨直接拥抱并兼容开放的 **x402 V2** 标准；
- ❌ **不做支付清算商，不运营公共 Facilitator**：我们不替全网垫付 Gas 或充当公共清算所，用户可以自由配置对接任何合规的 Facilitator；
- ❌ **不试图解决终端消费者的法律授权抗辩问题**：那是 AP2 或卡组织协议关注的领域；
- ❌ **不直接接入传统 Visa/Mastercard 卡组织令牌网络**：当前聚焦于原生契合机器微支付的稳定币（USDC）与内部高速虚拟钱包双轨；
- ❌ **不评判上游返回内容的“语义质量”**：如果上游 API 正常返回了 `200 OK` 和符合格式的 JSON，但里面的分析文章写得很烂，这属于应用层/模型评测问题，不属于金融网关的拦截范畴（付了钱拿到低质数据，属于明确的非目标）。

## 5. 开发者如何自己持续跟进这一领域？

Agent 基础设施正处于爆发初期的混战与收敛阶段，建议通过以下四个原则保持技术敏锐度：

1. **以中立基金会和官方 GitHub 仓库的一手规范为准**：优先查阅 x402 Foundation、FIDO Alliance、Model Context Protocol 官方仓库及各公司技术白皮书，少看二手营销软文；
2. **密切关注“治理归属”与“主版本号”的变迁**：同一套协议的治理主体（例如从单一科技巨头主导移交给 Linux Foundation 或 FIDO 等中立组织）和协议报文结构（如 x402 V1 到 V2）可能在几个月内发生重大演进；
3. **严格区分"PR 已发布/已公告"与"生产环境大规模可用"**：许多协议在概念发布初期只有 Demo 演示，距离具备完备的超时处理、重放保护和生产级 SDK 往往还有数月甚至更长的工程差距；
4. **对宣传口径的“交易量”保持独立审慎**：面对带有厂商市场推广性质的采用率或调用量数据，建议优先参考公开可查的链上合约交互数据（如 Dune Analytics 上的真实结算笔数）或独立第三方评测。

## 小结

- **分层视角**：各个 Agent 支付与商业方案**所处的架构层次不同、解决的核心痛点不同**（工具连接、电商结账、人类授权证明、机器微支付传输、实时金融风控）。
- **生态协同**：x402 是 AgentPay 链上轨所采用的底层支付传输协议；而 AgentPay 本身是架设在其上的**金融安全控制层**，并可与上层的 MCP、AP2 等协议无缝叠加。
- **动态演进**：该领域技术迭代极快，本篇全景梳理的时间锚点是 **2026-10-21**，在实际选型与集成时请务必核对各项目的最新官方状态。
