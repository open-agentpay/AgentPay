# Agent 自主度分级：辅助、半自主与全自主

## 一、为什么要区分 Agent 的自主度？

同样是 AI Agent，不同系统能够自行决定和执行的事情可能完全不同。

例如：

- Agent A：分析一份报告，并提出修改建议。
- Agent B：分析报告、修改文件，最后等待用户确认。
- Agent C：自动分析报告、修改文件并发布到指定平台。

三者都可以使用大模型和工具，但它们获得的执行权限不同。

如果不区分自主度，就很难回答一个关键问题：

**哪些事情可以让 Agent 自己决定，哪些事情必须由人来确认？**

自主度分级，就是帮助我们明确 Agent 的决策权、执行权和人工介入要求。

## 二、三个常见的自主度级别

本文采用一个便于工程实践的三级划分：辅助式、半自主式和全自主式。

这是一种用于理解和设计系统的实用分类，并非适用于所有行业的统一标准。

### 1. 辅助式 Agent：人决定，AI 辅助

在辅助式模式下，AI 主要负责分析信息、生成建议或准备操作，人类负责决定是否执行。

例如：

```text
用户提出任务
     ↓
AI 分析信息
     ↓
AI 生成建议
     ↓
用户检查结果
     ↓
用户决定是否执行
```

典型场景：

- 生成文章草稿。
- 分析业务数据。
- 提供代码修改建议。
- 生成待审批的操作方案。

这种模式适合高风险场景的早期探索，也适合执行结果需要人工判断的任务。

优点：

- 人类保留最终决定权。
- 容易发现明显错误。
- 不容易因为模型误判而直接执行外部操作。

缺点：

- 需要人工参与。
- 任务处理速度可能较慢。
- 人工检查仍可能遗漏问题。

需要注意：辅助式 Agent 即使不直接执行操作，也可能生成错误建议，因此关键结果仍需要核验。

### 2. 半自主式 Agent：AI 执行，人类把关

在半自主式模式下，Agent 可以在预先规定的范围内执行任务，但某些操作需要人工批准。

例如：

```text
用户提出任务
     ↓
AI 分析任务
     ↓
AI 执行低风险步骤
     ↓
是否需要审批？
   ┌─┴────┐
   │      │
  需要   不需要
   │      │
人工审批 继续执行
   │      │
   └──┬───┘
      ↓
   完成任务
```

典型场景：

- 自动搜索并整理行业资料。
- 自动生成报告，提交后等待审核。
- 自动生成邮件草稿，发送前由人确认。
- 自动分析交易机会，但下单需要授权。

这种模式兼顾了自动化效率与人工控制。

但审批机制必须真正有效。

如果 Agent 可以绕过审批接口直接调用底层工具，那么表面上的审批流程并不能形成可靠的安全边界。

### 3. 全自主式 Agent：在授权范围内自动执行

在全自主式模式下，Agent 可以在预先授权的范围内，自主决定并执行任务，无需每一步都等待人工确认。

例如：

```text
接收任务
    ↓
分析目标
    ↓
选择工具
    ↓
执行操作
    ↓
检查结果
    ↓
继续调整
    ↓
达到目标或触发停止条件
```

典型场景：

- 按固定规则整理文件。
- 自动监控公开数据并生成日报。
- 在严格限额内调用付费 API。
- 根据明确规则处理低风险、可逆的业务操作。

全自主并不意味着没有限制。

一个合理的全自主系统仍然需要：

- 明确的授权范围。
- 工具权限隔离。
- 最大执行次数。
- 时间和资源限制。
- 错误处理与恢复机制。
- 可追踪的执行记录。
- 必要时的自动停止机制。

**全自主描述的是执行过程中是否需要逐步等待人工批准，而不是 Agent 是否拥有无限权限。**

## 三、三种模式的对比

| 维度 | 辅助式 | 半自主式 | 全自主式 |
|---|---|---|---|
| 任务分析 | AI 参与 | AI 参与 | AI 参与 |
| 操作执行 | 主要由人决定并执行 | AI 可执行部分步骤 | AI 在授权范围内执行 |
| 人工介入 | 通常较多 | 在关键节点介入 | 不要求逐步批准 |
| 自动化程度 | 较低 | 中等 | 较高 |
| 运行效率 | 受人工流程影响 | 兼顾效率与控制 | 在合适任务中效率较高 |
| 主要风险 | 错误建议被采纳 | 审批机制被绕过 | 错误可能自动传播 |
| 适合场景 | 高风险决策、探索阶段 | 需要关键节点审批的流程 | 边界明确、可监控的任务 |

这三种模式不是简单的优劣排名。

对于低风险任务，全自主可能更高效；对于高风险操作，辅助式或半自主式往往更合适。

## 四、自主度不等于权限大小

这是设计 Agent 时最容易混淆的概念之一。

自主度回答的是：

> Agent 可以在多大程度上自行决定下一步？

权限回答的是：

> Agent 被允许执行哪些操作？

两者相互关联，但并不相同。

例如，一个 Agent 可以自主分析数据、选择查询策略，但只拥有只读数据库权限。

另一个 Agent 可能每一步都需要人工确认，却仍然拥有范围过大的文件系统访问权限。

因此，不能仅通过自主度判断系统是否安全。

设计时应分别考虑：

1. 决策自主度。
2. 工具访问权限。
3. 资金或资源限额。
4. 人工审批要求。
5. 运行时间与调用次数限制。

## 五、如何决定某个任务应该采用哪种模式？

可以从四个维度判断。

### 1. 操作风险

操作一旦执行，可能造成多大损失？

例如：

- 搜索公开信息：通常风险较低。
- 修改共享文件：可能影响其他人。
- 删除生产数据：风险较高。
- 转移真实资金：需要严格授权与控制。

风险越高，通常越需要限制权限或增加审批。

### 2. 操作是否可逆

如果操作出错，能否恢复？

例如：

- 生成一份草稿：通常可以重新生成。
- 修改文件：可能需要版本控制或备份。
- 删除数据：恢复成本可能较高。
- 已完成的链上交易：通常不能像普通数据库更新那样直接撤销。

越难撤销的操作，越应该谨慎设计自动执行条件。

### 3. 结果是否容易验证

如果系统能够通过明确规则判断结果是否正确，就更容易实现自动化。

例如：

```text
检查文件是否存在
检查 HTTP 状态码
检查金额是否超过限额
检查任务是否达到完成条件
```

如果结果高度依赖主观判断，或者缺乏可靠的数据来源，就可能需要人工复核。

### 4. 失败后能否安全恢复

如果执行失败，系统能否确认实际状态？

例如，一次 HTTP 请求超时，并不能证明服务端没有执行操作。

如果无法确认执行结果，系统就不应该简单地重复执行敏感操作。

需要先查询状态，或者进入专门的恢复流程。

## 六、建立任务风险与自主度的对应关系

下面是一种实用的初始设计方案：

| 任务类型 | 建议模式 | 主要控制措施 |
|---|---|---|
| 公开信息搜索 | 全自主式 | 调用限额、来源校验 |
| 文章草稿生成 | 辅助式或全自主式 | 内容审核、发布权限隔离 |
| 发送外部邮件 | 半自主式 | 收件人校验、发送前审批 |
| 修改生产数据 | 半自主式或受限自动执行 | 权限隔离、事务、备份、审计 |
| 执行真实资金转移 | 严格授权下的受限自动执行，必要时人工审批 | 金额限额、收款方校验、幂等、状态核验 |

这里的模式是设计建议，不是绝对规则。

例如，发送邮件也可以在明确授权的低风险场景中自动执行；资金操作也可以在严格限定的业务条件下实现自动化。但不能因为系统具备自动执行能力，就跳过相应的安全设计。

## 七、工程上如何控制 Agent 的自主度？

自主度不能只通过提示词控制，还应落实到程序架构中。

### 1. 限制工具范围

为不同任务注册不同的工具。

例如：

```text
数据分析 Agent
  ├── 查询公开数据
  └── 生成报告

不默认提供：
  ├── 删除生产数据
  ├── 修改账户权限
  └── 转移资金
```

没有必要的工具，就不应默认暴露给 Agent。

### 2. 为工具设置权限

即使两个 Agent 都可以查询数据库，它们能够访问的数据范围也可以不同。

例如：

- Agent A 只能读取公开数据。
- Agent B 可以读取某个项目的数据。
- Agent C 可以在审批后修改指定记录。

权限应由可信的服务端执行，而不是仅靠模型自行遵守。

### 3. 设置预算和执行上限

可以限制：

- 单次任务最大调用次数。
- 单次任务最大运行时间。
- 模型调用预算。
- API 消费额度。
- 单次操作金额。
- 一段时间内的累计操作额度。

这些限制可以降低任务循环和错误决策带来的影响。

### 4. 为敏感操作设置审批点

例如：

```text
AI 生成操作请求
       ↓
程序验证请求
       ↓
判断是否需要审批
       ↓
人工确认
       ↓
服务端重新校验
       ↓
执行操作
```

审批不能只是一条对话消息。

系统应确保实际执行路径确实受到审批状态约束，并防止请求被替换或重复执行。

### 5. 记录执行过程

至少应记录：

- 任务标识。
- 调用了什么工具。
- 关键参数与校验结果。
- 操作是否成功。
- 失败原因。
- 是否触发审批或停止条件。

对于敏感信息，应按照数据最小化原则处理日志，避免把密钥等机密内容直接写入日志。

## 八、一个逐步提升自主度的实践路线

开发 Agent 时，可以从低自主度开始，再根据验证结果逐步增加自动化程度。

### 阶段一：只生成建议

Agent 分析任务，但不直接执行外部操作。

重点验证模型是否理解目标、结果是否准确。

### 阶段二：自动执行只读操作

允许 Agent 查询数据、搜索信息和读取文件。

重点验证工具选择、权限隔离和执行日志。

### 阶段三：执行可逆操作

允许 Agent 在受控环境中修改草稿、创建临时文件或执行其他容易恢复的操作。

重点验证错误恢复、状态管理和重复执行保护。

### 阶段四：有限范围内自动执行

为明确授权的操作配置额度、频率、审批条件和停止规则。

重点验证异常情况下系统能否安全停止，以及能否恢复到可确认的状态。

### 阶段五：根据实际风险决定是否扩大权限

只有在系统已经通过充分测试、监控和安全评估后，才考虑扩大自动执行范围。

**自主度应该根据验证结果逐步提升，而不是一开始就把所有权限交给 Agent。**

## 九、小结

Agent 自主度可以分为三种常见模式：

- **辅助式**：AI 提供建议，人类决定和执行。
- **半自主式**：AI 可以执行部分任务，关键操作需要审批。
- **全自主式**：AI 可以在预先授权的范围内自动完成任务。

真正重要的不是让 Agent 尽可能自主，而是明确它可以做什么、不能做什么，以及出错后如何停止和恢复。

可以记住一个原则：

**自主度决定 Agent 可以自行决定多少事情，权限决定 Agent 实际能够执行什么操作，安全机制则负责限制错误和风险的影响范围。**
