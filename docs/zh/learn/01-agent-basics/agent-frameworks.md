# Agent 开发框架：LangChain、CrewAI 等框架的位置

## 一、为什么会出现 Agent 框架？

最开始开发一个 Agent，可能只需要完成几个步骤：

1. 调用模型。
2. 解析模型的工具调用请求。
3. 执行工具。
4. 把结果返回模型。
5. 生成最终回答。

但随着系统变复杂，开发者还需要处理：

- 多轮工具调用。
- 多步骤任务规划。
- 对话状态和记忆。
- 工具执行错误。
- 工作流分支。
- 人工审批。
- 长时间运行任务。
- 执行日志和调试。
- 多个 Agent 之间的协作。

如果所有逻辑都从零开始编写，代码会越来越复杂。

Agent 框架的作用，就是提供一组可复用的抽象和基础能力，降低开发复杂 Agent 的成本。

**框架可以帮助组织 Agent，但不会自动保证 Agent 的正确性、安全性或业务价值。**

## 二、Agent 框架在整个系统中的位置

一个典型的 Agent 应用可以拆成以下层次：

```text
用户 / 业务系统
       ↓
应用业务逻辑
       ↓
Agent 框架 / Agent Runtime
       ↓
模型 API
       ↓
模型服务
```

Agent 框架还可能负责连接：

```text
Agent Runtime
 ├── Tools
 ├── MCP Clients
 ├── Memory
 ├── Workflow
 ├── State
 └── Observability
```

这些模块的具体边界取决于框架和应用设计，并不是所有框架都包含全部能力。

更重要的是，业务权限、数据库事务、资金限制等关键规则，不应该仅仅依赖框架约定。

## 三、常见 Agent 开发框架

### 1. LangChain

LangChain 提供用于构建 LLM 应用和 Agent 的开发组件。

它适合需要组合模型、工具、检索和外部服务的应用。

常见使用场景：

- 为模型注册工具。
- 连接向量数据库和检索系统。
- 组合多个模型调用步骤。
- 构建带工具调用的 Agent。
- 集成不同模型供应商。

它的主要价值是提供可复用的集成组件，减少重复开发。

需要注意：LangChain 不是一个自动解决所有任务的智能体。实际执行路径、状态管理、错误处理和权限控制仍然需要合理设计。

官方文档：https://docs.langchain.com/

### 2. LangGraph

LangGraph 侧重于构建具有状态、分支、循环和持久化能力的多步骤 Agent 工作流。

它适合：

- 需要多个执行阶段的任务。
- 需要根据中间结果进行分支决策。
- 需要保存执行状态。
- 需要暂停并等待人工审批。
- 需要处理中断、恢复和长时间运行任务。

可以将它理解为帮助开发者组织复杂执行流程的工具。

例如：

```text
开始
  ↓
分析任务
  ↓
执行工具
  ↓
检查结果
  ├── 不满足条件 → 再次执行
  └── 满足条件 → 输出结果
```

对于需要明确状态和恢复机制的系统，这类能力尤其有用。

官方文档：https://docs.langchain.com/oss/python/langgraph/overview

### 3. CrewAI

CrewAI 侧重于组织多个具有不同角色的 Agent 协作完成任务。

例如，构建一套研究流程：

```text
研究 Agent
    ↓
分析 Agent
    ↓
审核 Agent
    ↓
报告生成
```

不同 Agent 可以使用不同的指令、工具和职责。

适合考虑多角色任务分工的场景，例如资料研究、内容分析和多阶段报告生成。

不过，多 Agent 并不意味着任务一定更准确。

多个 Agent 会增加模型调用次数、通信成本和协调复杂度。对于简单任务，单 Agent 或确定性工作流可能更合适。

官方文档：https://docs.crewai.com/

## 四、这些框架之间是什么关系？

它们不是必须三选一的同类产品，也不代表只能按照某种固定方式组合。

| 框架 | 主要关注点 | 适合考虑的场景 |
|---|---|---|
| LangChain | LLM 应用与工具集成 | 需要快速组合模型、工具和检索能力 |
| LangGraph | 状态化执行与工作流控制 | 需要分支、循环、持久化和恢复 |
| CrewAI | 多 Agent 角色协作 | 任务适合拆分为多个协作角色 |

实际项目中，可以只使用其中一个，也可以组合不同组件。

选择时应先明确业务问题，再决定需要什么抽象，而不是为了使用框架而使用框架。

## 五、自己写代码，还是使用框架？

### 方案 A：自己实现最小 Agent

基本结构如下：

```python
def run_agent(task):
    messages = [{"role": "user", "content": task}]

    for _ in range(10):
        response = call_model(messages)

        if not response.tool_calls:
            return response.content

        for tool_call in response.tool_calls:
            result = execute_allowed_tool(tool_call)
            messages.append(format_tool_result(tool_call, result))

    raise RuntimeError("超过最大执行次数")
```

这是一个简化的伪代码示例，`call_model`、`execute_allowed_tool` 和 `format_tool_result` 需要自行实现。

优点：

- 逻辑直接。
- 容易理解执行过程。
- 可以针对业务设计精确的限制。
- 依赖相对少。

缺点：

- 需要自行实现工具调度、状态管理、异常处理等能力。
- 功能扩展后可能积累大量基础设施代码。

### 方案 B：使用 Agent 框架

优点：

- 可以复用已有组件。
- 更容易构建复杂执行流程。
- 部分框架提供状态管理、追踪和人工介入机制。

缺点：

- 需要理解框架的抽象。
- 依赖升级可能影响实现。
- 调试时需要同时理解业务代码和框架行为。
- 框架提供的能力不一定符合所有业务需求。

## 六、如何选择合适的方案？

可以按以下顺序判断。

### 第一步：任务是否需要动态决策？

如果任务是固定的：

```text
接收订单 → 校验订单 → 扣减库存 → 发送通知
```

优先考虑确定性工作流。

如果任务需要根据中间结果调整下一步，例如多轮搜索和信息核验，可以考虑 Agent。

### 第二步：执行流程是否复杂？

如果只是一次工具调用，普通函数加模型 API 可能已经足够。

如果涉及大量分支、状态保存、暂停恢复和人工审批，可以考虑更完善的执行框架。

### 第三步：是否需要多 Agent 协作？

先判断任务是否真的需要多个角色。

如果只是把同一任务拆成几个简单步骤，普通工作流可能更简单。

只有在角色职责、上下文或执行策略确实不同的情况下，才值得引入多 Agent 协作。

### 第四步：安全和可靠性如何实现？

无论选择哪种框架，都需要独立考虑：

- 工具权限。
- 输入参数校验。
- 最大执行次数。
- 超时与重试。
- 成本和资源限制。
- 敏感操作审批。
- 日志与审计。
- 故障恢复。

这些要求不能因为采用了成熟框架就自动视为已经满足。

## 七、一个实用的工程原则

开发 Agent 时，可以从简单方案开始，逐步增加必要的复杂度：

```text
模型 API
   ↓
工具调用
   ↓
带限制的执行循环
   ↓
状态管理与错误恢复
   ↓
复杂工作流
   ↓
必要时再引入多 Agent
```

每增加一层，都应该对应一个明确的问题和可验证的收益。

例如，只有在需要保存复杂状态、处理分支或恢复中断时，才考虑引入专门的状态化工作流框架。

## 八、小结

理解 Agent 框架，需要记住三个要点：

1. 框架是组织代码和执行流程的工具，不是 Agent 本身。
2. 不同框架的关注点不同，应根据任务特点选择。
3. 框架不能替代业务规则、安全控制和可靠性设计。

**先把任务和执行边界设计清楚，再选择框架，通常比先选框架再寻找应用场景更有效。**
