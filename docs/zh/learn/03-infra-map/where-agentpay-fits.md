# AgentPay 的位置

::: warning 实验性项目
AgentPay 尚未经过独立安全审计，请勿用于生产环境的真实资金。
:::

## 一句话结论

AgentPay 是横亘在 Agent（大脑）与真实资金（钱包）之间的**零信任金融控制层（Financial Control Layer）**：
* **在付款发生之前**：作为确定性的风控防火墙，拦截越权、超支与异常高频请求，判断**“这笔钱该不该付”**；
* **在付款进行之中**：通过原子预留与双轨路由，接管复杂的并发锁与签名协调，决定**“怎么安全地付”**；
* **在付款发生之后**：通过三态状态机与不可变审计日志，保证**“超时不重付、失败可恢复、账目可追溯”**。

它不是大模型编排框架，不是底层支付通信协议，也不是公链或托管银行。

## 它具体负责什么（七大核心职责）

为了让“金融控制”落地，AgentPay 将职责细化为以下七个具体的工程模块：

### 1. 付款前的确定性风控（Pre-Payment Policy Evaluation）
大模型是概率性的，但财务风控必须是 100% 确定性的。在任何加密签名生成之前，AgentPay 强制执行四道防线：
* **单笔硬顶（Per-Tx Limit）**：例如限制单次 API 调用不得超过 `0.50 USDC`，防止卖方接口突然调价（价格刺客）或模型被诱导购买高价服务。
* **滚动周期预算（Rolling Budget）**：支持按小时、天、月或项目生命周期设定总预算上限。
* **收款方与网络白名单（Allowlist）**：严格校验收款钱包地址（`payTo`）、代币合约地址及目标链（如仅允许 `Base Mainnet`），彻底阻断因提示词注入（Prompt Injection）导致的向黑客地址打款。
* **速率熔断与死循环检测（Velocity & Loop Circuit Breaker）**：当 Agent 因解析报错陷入 `while(true)` 死循环重试时，按滑动时间窗口（如“1 分钟内向同一接口付款不得超过 5 次”）自动触发熔断器锁死支出。

### 2. 预算的原子预留（Atomic Budget Reservation）
在多 Agent 协同或异步并发调用场景下，“先查余额、再付款、最后扣减”的传统逻辑会导致严重的并发超支（Race Condition）。
* **例子**：预算还剩最后 `1.00 USDC`，Agent 同时并发请求 5 个单价 `0.50 USDC` 的数据源。如果只做简单读取，5 个请求都会认为余额充足并签出付款，最终花费 `2.50 USDC`。
* **AgentPay 的做法**：引入类似银行信用卡预授权的 **两阶段状态机（Reserve $\rightarrow$ Commit / Release）**。请求通过风控的瞬间，系统原子性地冻结（Reserve）对应额度；只有拿到额度锁的请求才能进入签名环节，彻底杜绝并发透支（详见 [预算预留](../04-agentpay-concepts/budget-reservation.md)）。

### 3. “付款-结算-交付”分离与三态恢复（Tri-State Recovery）
一次付费 API 调用包含三个独立阶段：**买方签出授权（Payment） $\rightarrow$ 资金上链/入账（Settlement） $\rightarrow$ 卖方返回业务数据（Delivery）**。在真实网络中，任何一步都可能超时。
* **核心职责**：AgentPay 绝不把网络超时（Timeout）简单等同于失败（Failure）。当请求处于 **`Unknown / In-Flight`（结果未知）** 状态时，AgentPay 会锁住该笔交易的幂等键（Idempotency Key），**严禁客户端生成新的付款签名进行盲目重试**，而是转入结果查询与状态恢复流程，确保“一分钱不会付两次”（详见 [超时不等于失败](../04-agentpay-concepts/timeout-is-not-failure.md)）。

### 4. 显式的双轨支付路由（Dual-Rail Payment）
不同的业务场景对延迟和去中心化程度的要求不同。AgentPay 同时支持两条支付轨道：
1. **链上支付轨（x402 路径）**：基于 EIP-3009 等无 Gas 授权签名，通过区块链稳定币（如 USDC）完成无需信任的跨组织结算。
2. **平台钱包轨（Ledger 路径）**：基于网关内部的高性能双式记账账本，实现毫秒级、零链上成本的微支付扣费。
* **安全铁律（严禁静默降级）**：哪条路由可用由策略显式声明。如果买方指定走平台钱包但余额不足，AgentPay 会直接拒绝报错，**绝不会在后台静默切换去动用买方的链上私钥签名**，确保资金流向完全符合预期。

### 5. 零代码改造的卖方收费网关（Seller Monetization Gateway）
对于 API 提供方（卖方），不需要在自己的 Python/Java 业务代码里写任何区块链验签或账本扣费逻辑。
* **核心职责**：将 Go 网关挡在你的业务服务前面作为反向代理。网关全权负责：拦截未付费请求并下发 `HTTP 402` 报价单 $\rightarrow$ 校验买方发来的付款凭证并完成清算 $\rightarrow$ 注入上游真实的内部鉴权 Key 转发请求 $\rightarrow$ 若上游服务崩溃（如返回 `502/504`），自动触发退款或释放预留额度，保护买方权益。

### 6. 多租户、权限隔离与一键急停（Multi-Tenancy & Kill Switch）
面向企业级与团队场景，提供完善的组织治理结构：
* **层级隔离**：支持 `租户 (Tenant) -> 项目 (Project) -> Agent 实例` 的多级管理，每个 Agent 拥有独立的身份凭证（API Key）与专属预算池。
* **配置安全发布**：策略与路由修改采用 **“草稿编辑 $\rightarrow$ 静态校验 $\rightarrow$ 版本发布 $\rightarrow$ 一键回滚”** 的工程化生命周期，防止管理员手滑改错配置导致线上事故。
* **紧急制动（Kill Switch）**：当发现某个 Agent 行为失控或密钥疑似泄露时，管理员可在控制台**一键停用（Freeze）**该 Agent，毫秒级切断其所有外发支付权限。

### 7. 全链路不可变审计（Immutable Audit Trail）
财务系统的底线是“账目可查”。AgentPay 会将每一次请求拆解为标准化的审计事件流（Audit Events）：
* 无论是放行还是拒绝，都会精确记录：*哪个 Agent、在哪个会话（Session）中、为了调用哪个路由、报价多少、命中了哪条风控规则、为什么被拦截（或放行）、对应的预留单号与链上交易哈希是什么*。财务与安全人员可随时在审计时间线中完整还原现场。

## 它不负责什么（七大“不越界”原则）

在安全基础设施的设计中，**克制与明确边界**比堆砌功能更重要。以下是 AgentPay 明确**不做**的事情，以及背后的架构原因与应对建议：

| AgentPay 绝不负责 | 为什么不越界（架构原因） | 真实场景反例与正确做法 |
|---|---|---|
| **1. Agent 的业务推理与任务编排** | 决定“先查财报还是先查新闻”是模型与编排框架（LangChain、CrewAI、AutoGen）的职责。将业务推理与金融风控解耦，才能保证防火墙的纯粹与通用。 | **反例**：指望 AgentPay 帮 Agent 规划出最省钱的搜索关键词。<br>**正确做法**：用 LangChain 编排任务流，将 AgentPay 作为底层的 HTTP Client 或 Tool Wrapper 嵌入其中。 |
| **2. 发明私有的底层支付协议** | 造封闭的支付轮子会割裂生态。链上交互必须遵循开放标准，才能与生态中的其他工具互通。 | **正确做法**：链上路径严格遵循开放的 **x402 V2 协议标准**。AgentPay 是协议的**守护者与执行者**，而非协议制定者（详见 [AgentPay 与 x402](./agentpay-vs-x402.md)）。 |
| **3. 评估返回内容的质量（值不值）** | 防火墙工作在协议与规则层，它能看懂价格、地址和 HTTP 状态码，但无法对返回数据的业务价值做语义评判。 | **反例**：Agent 花了 `0.1 USDC` 买了一份合规接口返回的天气预报，但内容其实是过期的。只要价格在预算内、地址在白名单内且返回 `HTTP 200`，AgentPay 就会正常放行结算。<br>**正确做法**：通过白名单机制严格筛选信誉良好的上游卖家。 |
| **4. 替买方托管链上私钥** | 集中托管私钥意味着网关一旦被黑，所有买方的链上资产将面临灭顶之灾。AgentPay 坚持**非托管（Non-Custodial）**原则。 | **正确做法**：在链上支付路径中，私钥永远留在买方自己的运行环境（本地内存、KMS 或硬件签名器）中。网关和清算服务只接收签好名的授权凭证（如 EIP-3009 Payload），绝不触碰私钥原文。 |
| **5. 充当法币银行、支持提现或转账** | 涉及资金充提、跨用户转账与资金池沉淀会触及复杂的金融合规监管（如 KYC/AML 与支付牌照）。 | **正确做法**：当前版本的平台虚拟钱包（Platform Wallet）仅定位为**闭环消费的内部记账账本**（类似云厂商的代金券/算力点账户），用于低延迟扣费测试与内部核算，不支持提现，也不支持用户间 P2P 转账。 |
| **6. 运营中心化的公共清算网络** | 成为公共清算所意味着承担商业运营与流动性兜底责任，这超出了开源基础设施项目的定位。 | **正确做法**：代码库中提供了**清算服务（Facilitator / Settlement Service）的完整参考实现**（包含真实链上广播版与本地 Mock 版），供开发者自建、集成或用于端到端测试。 |
| **7. 抵御买方宿主机级别的彻底沦陷** | 如果运行 Agent 的服务器本身已经被黑客拿到了 `root` 权限，攻击者可以直接绕过 Python SDK 读取环境变量里的私钥。 | **正确做法**：本地 SDK 防火墙防的是**“应用层失控”**（如模型幻觉、Prompt 注入、代码死循环、恶意第三方工具）。如需防范宿主机沦陷，需配合 TEE（可信执行环境）或远程硬件签名机，这属于后续的进阶安全规划。 |

## 三类角色，三种接入视角

根据你在生态中所处的位置，你只需要接触 AgentPay 的特定切面，无需理解所有内部细节：

### 角色一：买方开发者（让 Agent 安全地花钱）

**你的痛点**：你正在用 Python 开发一个自主 Agent，希望它能按需购买外部数据或算力，但你极度担心它因为 Bug 或被注入攻击而在半夜刷爆你的钱包。

* **你用到的组件**：仅需 **`Python SDK`**（内含客户端拦截器、本地策略引擎与签名协调器）。
* **工作方式**：
    1. 在代码中初始化 AgentPay 客户端，配置本地策略（例如：`单笔上限 = 0.2 USDC`，`日预算 = 5 USDC`，`白名单域名 = ["api.trusted-data.com"]`）。
    2. 将该客户端包装成标准的 HTTP Session 或 LangChain `@tool` 交给 Agent 使用。
    3. 对大模型而言，它只管发起普通的工具调用；底层的 `402 捕获 -> 策略校验 -> 本地私钥签名 -> 重发请求` 全部由 SDK 在后台无感完成。
* **部署成本**：**零服务端部署**。最小可用模式下，不需要启动网关或数据库，一个轻量级 SDK 即可在本地进程内筑起防火墙。

### 角色二：卖方服务商（把现有 API 变成按次收费接口）

**你的痛点**：你开发了一个高质量的行业研报 API 或 MCP 工具，想向全球的 AI Agent 按次收取稳定币（或平台额度），但你不想在自己现有的业务代码里写任何复杂的区块链验签、防重放和账本逻辑。

* **你用到的组件**：**`Go 网关 (Gateway)`** + **`Web 控制台`**。
* **工作方式**：
    1. 将 Go 网关部署在你的业务 API 前面（作为反向代理）。
    2. 在控制台中添加一条路由规则：将外部路径 `/v1/research` 映射到你的内部服务，设置单价为 `0.05 USDC`，指定你的收款钱包地址。
    3. 网关会自动将你上游服务的真实鉴权密钥（如内部 Bearer Token）安全托管在服务端。
    4. 当外部 Agent 请求该接口时，网关全权负责开具 402 报价单、校验付款、处理并发幂等；只有确认收款无误后，才会替换上内部密钥将请求转发给你的业务服务。
* **改造成本**：**上游业务代码零改动**。

### 角色三：团队与财务管理员（集中管控多 Agent 与资金池）

**你的痛点**：你在一家企业或工作室里管理着十几个不同职能的 Agent（投研、客服、自动化运营），需要把控团队的整体 AI 支出，并在出现异常时能迅速定位和止损。

* **你用到的组件**：**`Web 控制台`** + **`Go 网关`**。
* **工作方式**：
    1. **权限与预算分配**：在控制台创建不同的项目（Project），为每个 Agent 签发独立的 API Key，并分配各自的每日预算池。
    2. **安全变更（Draft & Publish）**：修改收费路由或风控策略时，先在草稿箱（Draft）中编辑，通过系统自动合规校验后再正式发布（Publish）；如果新策略导致正常业务被误杀，可一键回滚（Rollback）到上一历史版本。
    3. **全息审计与急停**：在审计时间线（Audit Timeline）中按会话或 Agent 检索每一笔钱的去向。一旦收到高频拦截告警，点击 **“一键停用”** 即可瞬间冻结问题 Agent 的所有消费能力。

## 核心组件与运行形态一览

### 五大核心组件

| 组件名称 | 核心技术栈与职责 | 主要服务对象 |
|---|---|---|
| **Python SDK** | 客户端 HTTP 拦截器、进程内本地策略引擎、EIP-3009/x402 签名协调器、框架工具包装器 | 买方开发者 |
| **Go 网关 (Gateway)** | 高性能反向代理、402 报价签发与凭证校验、原子预算锁、平台虚拟钱包账本、三态幂等恢复引擎 | 卖方服务商、团队管理员 |
| **Web 控制台 (Console)** | 路由与风控策略可视化编排、草稿校验与版本发布/回滚、多租户与 Agent 密钥管理、交互式审计时间线 | 团队管理员、财务审计 |
| **清算服务 (Facilitator)** | 负责验证链下授权签名并将其打包广播至区块链网络的标准参考实现（同时提供本地零延迟 Mock 版本） | 架构演示、集成开发者 |
| **规范与测试向量 (Specs)** | 协议交互格式、状态机流转契约、标准错误码字典、审计事件 Schema 的跨语言权威定义 | 核心贡献者、二次开发者 |

### 两种运行形态

AgentPay 的架构设计支持从“单机快速验证”平滑过渡到“生产级分布式部署”：

1. **本地嵌入/沙盒模式（All-in-One Mode）**
    * **特点**：买方 Agent、网关、模拟清算服务与模拟上游 API 全部在本地一键拉起，无需连接外部公链，无需真实代币。
    * **适用场景**：本地代码开发、自动化集成测试、快速概念验证（运行仓库中的 `make demo` 即是此形态）。
2. **分布式云端模式（Distributed Mode）**
    * **特点**：买方 Agent 带着 Python SDK 运行在用户自己的私有环境（私钥不出本地）；Go 网关、Web 控制台与清算服务独立部署在云端服务器，各方通过标准 HTTPS 与 x402 协议头通信。
    * **适用场景**：多 Agent 团队协作、对外提供商业化付费 API、真实的跨组织机器间交易。

## 常见问题（FAQ）

### Q1：我只是想保护我自己的一个 Python Agent 别乱花钱，必须去服务器上部署 Go 网关和 Web 控制台吗？
**完全不需要。**
这是最常见的误解。如果你只是纯粹的**买方**，且不需要跨机器共享预算池，你只需要在 Python 项目里引入 `AgentPay SDK`。SDK 内部已经内置了一个完整的**本地策略引擎（Local Policy Engine）**，单笔限额、总预算控制、收款地址白名单和死循环频率熔断全部可以在本地进程内独立完成，零外部服务依赖。

### Q2：AgentPay 是一个加密钱包（Crypto Wallet）产品吗？
**不是。**
* 在**链上支付路径**中，AgentPay 只是一个“守门员”。你依然使用自己原有的加密钱包与私钥（通过环境变量或安全模块传入），AgentPay 负责在签名生成前做规则校验。
* 在**平台虚拟钱包路径**中，网关内部的钱包本质上是一个**高并发记账账本（Ledger）**，旨在解决高频微支付（如每次调用 `0.001` 美元）在链上结算延迟高、Gas 划不来的问题，它并不是一个面向终端C端用户的钱包 App。

### Q3：如果卖方收了我的钱，但是它的服务器崩溃了（比如返回 HTTP 500），我的钱会打水漂吗？
如果卖方使用了 **AgentPay Go 网关**，你的资金会受到状态机的严格保护：
网关会将“预算锁定/扣费”与“上游交付结果”绑定。当网关转发请求给卖方上游业务服务，发现上游返回 `5xx` 崩溃错误或连接拒绝时，网关会根据预设的恢复策略自动回滚（Release）刚才预留的额度，或者将凭证标记为未消费状态，确保买方不会因为卖方的服务端故障而白白蒙受损失。

### Q4：它能无缝接入我现有的 LangChain、CrewAI 或自研 Agent 框架吗？
**完全可以，且无需重构你现有的 Agent 逻辑。**
AgentPay 在客户端工作在底层的 HTTP 传输层（基于 `httpx` / `requests` 拦截器封装）或工具装饰器层。你只需要把原本直接发起 `requests.get()` 的代码换成 AgentPay 提供的安全客户端实例，上层的 Prompt、模型推理和框架编排代码一行都不用改。
