## 1. Core Design Principles

1. **Strict Orthogonal Separation of Three State Lines**:
   - **PaymentIntent**: End-to-end business request lifecycle.
   - **Settlement**: Fund transfer state supporting **dual-rail payment methods (`Payment Method`)**:
     - `onchain` (On-chain settlement): x402 challenge signing, blockchain broadcast, and block confirmation.
     - `wallet` (Internal virtual wallet): Strongly transactional fund reservation (`Hold`), confirmed deduction (`Capture`), and reservation release (`Release`).
   - **Fulfillment**: Actual delivery state of the target upstream API resource/response.
2. **`unknown` as a First-Class State**:
   - Whenever a settlement or fulfillment outcome is ambiguous, **it must never be assumed successful or assumed failed**.
   - Wallet deductions execute within local database transactions and have no settlement `unknown` state; however, **if fulfillment enters `unknown`, the wallet hold must remain locked and transition the intent to `needs_review`**—never auto-releasing or auto-capturing.
3. **Terminal State Immutability**:
   - Once an entity enters a terminal state (`completed`, `failed`, `expired`, `rejected`, `confirmed`, `released`), its state is strictly read-only; only immutable audit events may be appended.
4. **No Blind Retries & No Silent Downgrades**:
   - Blindly re-charging or re-broadcasting an `unknown` state is strictly prohibited.
   - **No Auto-Downgrade**: If a virtual wallet has insufficient balance, the gateway must immediately return `402 Insufficient Balance` and must never silently fall back to an on-chain charge, preventing unexpected on-chain expenditures.

## 2. Identifiers & Multi-Tenant Idempotency Contract

| Identifier | Scope & Responsibility | Constraint Rules |
|---|---|---|
| `request_id` | Single HTTP request trace | Generated by the gateway upon inbound arrival (UUIDv4) and propagated across all structured logs |
| `idempotency_key` | Client business-level idempotent retry | Unique per tenant. Identical keys within the same tenant strictly map to the same `payment_intent_id` |
| `payment_intent_id` | High-level payment intent | One `idempotency_key` maps uniquely to one intent (format: `pi_...`) |
| `hold_id` | Virtual wallet reservation ID | Exclusive to the wallet path; one intent binds uniquely to one active Hold (format: `hld_...`) |
| `settlement_id` | Settlement record ID | One intent corresponds to at most one active settlement at any time (format: `stl_...`) |
| `fulfillment_id` | Upstream business delivery attempt | One intent corresponds strictly to one fulfillment record (format: `ful_...`) |

## 3. Dual-Rail Settlement & Fulfillment State Flows

### 3.1 On-Chain Settlement Path
Follows **Scheme A (Settle Before Fulfill)**:
```text
authorized ──▶ submit ──▶ [submitted] ──▶ [pending] ──▶ [confirmed]
                                                             │ (dispatch)
                                                             ▼
                                                    [fulfillment: in_progress]
                                                             ├─ 2xx ─▶ completed
                                                             ├─ 4xx ─▶ refund_required
                                                             └─ 5xx ─▶ needs_review
```

### 3.2 Internal Virtual Wallet Path
Follows the **"Hold → Fulfill → Capture / Release"** closed loop:
```text
authorized ──▶ hold ──▶ [held] ──(dispatch)──▶ [fulfillment: in_progress]
                                                        ├─ 2xx ─▶ capture ──▶ confirmed (completed)
                                                        ├─ 4xx ─▶ release ──▶ released (unbilled release)
                                                        └─ 5xx ─▶ keep held ──▶ needs_review (manual review)
```

**Dual-Rail Advantage**:
- In the wallet path, when the upstream explicitly fails with a 4xx error, the gateway simply executes an in-database transactional `release` to unfreeze the hold—**eliminating complex refund or compensation workflows**, guaranteeing zero financial loss for the buyer and zero unpaid service delivery for the seller.

## 4. Three-Dimensional State Definitions & Valid Transition Matrix

### 4.1 Payment Intent (`PaymentIntent`)

| Current State | Trigger Event | Target State | Description & Guard Conditions |
|---|---|---|---|
| `created` | `challenge_issued` | `challenged` | On-chain path only: HTTP 402 challenge sent |
| `created` | `payload_verified` | `authorized` | Wallet path only: API Key and budget checks passed |
| `created` | `policy_denied` | `rejected` | Denied by policy, blocked by risk control, or wallet frozen in arrears |
| `challenged` | `payload_verified` | `authorized` | On-chain path: buyer retries request with valid signature |
| `challenged` | `payload_invalid` | `rejected` | Invalid signature, tampered payload, or malformed format |
| `challenged` | `timeout` | `expired` | Challenge TTL (default 300s) elapsed without submission |
| `authorized` | `settlement_confirmed` | `completed` | On-chain `confirmed` + fulfillment succeeded, or wallet `capture` succeeded |
| `authorized` | `settlement_failed` | `failed` | On-chain settlement failed, or insufficient wallet balance for hold |
| `authorized` | `settlement_released` | `failed` | Wallet path: hold released after upstream failure; intent closed unbilled |
| `authorized` | `authorization_expired`| `expired` | On-chain authorization expired before settlement started |
| `authorized` | `recovery_deadline_exceeded`| `needs_review` | Settlement or fulfillment remained `unknown` past recovery deadline |
| `needs_review`| `manual_resolved_confirmed`| `completed`| Manual operator verification confirmed payment and delivery |
| `needs_review`| `manual_resolved_failed` | `failed` | Manual operator verification confirmed non-delivery and closed intent |

### 4.2 Settlement (`Settlement`)

| Current State | Trigger Event | Target State | Payment Method & Rule |
|---|---|---|---|
| `not_started` | `hold_acquired` | `held` | [Wallet] Quota successfully frozen in database transaction |
| `not_started` | `hold_failed` | `failed` | [Wallet] Insufficient available balance or wallet frozen |
| `held` | `capture` | `confirmed` | [Wallet] Upstream returned 2xx; deduction captured to ledger (terminal) |
| `held` | `release` | `released` | [Wallet] Upstream returned 4xx; hold released back to available balance (terminal) |
| `not_started` | `submit_ok` | `submitted` | [On-Chain] Broadcast succeeded and returned `tx_hash` |
| `not_started` | `submit_rejected_definitely` | `failed` | [On-Chain] Deterministically rejected by RPC node |
| `not_started` | `submit_timeout` | `unknown` | [On-Chain] Submission timed out; state unknown |
| `submitted` | `seen_on_chain` | `pending` | [On-Chain] Transaction observed in mempool or mined block |
| `submitted` | `query_timeout` | `unknown` | [On-Chain] Receipt query timed out |
| `pending` | `confirmations_reached` | `confirmed` | [On-Chain] Reached required block confirmations (terminal) |
| `pending` | `reverted` | `failed` | [On-Chain] Transaction execution reverted on-chain (terminal) |
| `pending` | `query_timeout` | `unknown` | [On-Chain] Confirmation polling timed out |
| `unknown` | `query_found_confirmed` | `confirmed` | [On-Chain] Reconciliation probe confirmed block inclusion |
| `unknown` | `query_found_failed` | `failed` | [On-Chain] Reconciliation probe confirmed failure and expired unspent |
| `unknown` | `query_found_pending` | `pending` | [On-Chain] Pending transaction rediscovered on-chain |
| `unknown` | `query_still_unknown` | `unknown` | [On-Chain] Transaction state remains unknown |

### 4.3 Business Fulfillment (`Fulfillment`)

| Current State | Trigger Event | Target State | Description & Safety Guards |
|---|---|---|---|
| `not_started` | `dispatch` | `in_progress` | Requires `settlement==confirmed` (on-chain) or `settlement==held` (wallet) |
| `in_progress` | `upstream_2xx` | `succeeded` | Upstream delivery succeeded (triggers wallet `capture`) |
| `in_progress` | `upstream_4xx` | `failed` | Upstream rejected client input without execution (triggers wallet `release`) |
| `in_progress` | `upstream_5xx` | `unknown` | Upstream server error; cannot assume unexecuted (wallet keeps `held`) |
| `in_progress` | `upstream_timeout`| `unknown` | Connection dropped or read timed out (wallet keeps `held`) |
| `unknown` | `upstream_status_query_ok` | `succeeded` | Idempotent probe confirmed upstream succeeded (triggers delayed `capture`) |
| `unknown` | `upstream_status_query_failed` | `failed` | Idempotent probe confirmed upstream did not execute (triggers delayed `release`) |
| `unknown` | `recovery_deadline_exceeded` | `unknown` | Exceeded max recovery window; flagged for manual review |

## 5. External Composite View Mapping

| Settlement State | Fulfillment State | Derived Display Status | Business Interpretation |
|---|---|---|---|
| `held` | `not_started` / `in_progress` | `WALLET_HOLD_PROCESSING` | Wallet quota reserved; upstream service call in progress |
| `unknown` / `pending` / `submitted` | `not_started` | `SETTLEMENT_IN_PROGRESS` | On-chain payment settlement in progress |
| `confirmed` | `in_progress` | `FULFILLMENT_IN_PROGRESS` | Payment confirmed; upstream service delivery in progress |
| `confirmed` | `succeeded` | `COMPLETED` | Transaction and fulfillment completed successfully |
| `confirmed` | `failed` | `SETTLED_FULFILLMENT_FAILED_REFUND_REQUIRED` | On-chain payment settled but fulfillment failed; refund required |
| `confirmed` | `unknown` | `SETTLED_FULFILLMENT_UNKNOWN_NEEDS_REVIEW` | Payment confirmed, but fulfillment outcome is ambiguous and needs review |
| `released` | `failed` | `RELEASED_UNBILLED` | Wallet hold released; zero funds deducted |
| `failed` | `not_started` | `PAYMENT_FAILED` | Payment failed prior to fulfillment; zero funds deducted |
