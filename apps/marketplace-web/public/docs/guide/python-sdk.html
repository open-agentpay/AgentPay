Python SDK Guide ​

The agentpay package is the Python SDK for AI agents and API providers. It gives your agent a drop-in HTTP client that handles paid APIs for you while a local financial firewall decides whether each payment is allowed.

Experimental

AgentPay is unaudited and intended for testnet and sandbox use only. Never put real funds on a key used with it.

What the SDK gives you ​

CapabilityDescription
AgentPayClientA subclass of httpx.Client. Use it exactly like httpx: get, post, timeouts, headers.
Two payment modesPrice-aware wallet mode (API key, x402-style agentpay-wallet challenge, tenant virtual wallet) and on-chain mode (local signer, x402 + EIP-3009).
Local financial firewallA policy engine (per-tx cap, rolling budget, whitelist, circuit breaker). With wallet challenge mode enabled, it checks the quoted price before the gateway places a hold.
Audit metadataOptional headers that group an agent's calls into sessions and tasks in the console timeline.
Integrationspaid_tool for LangChain / CrewAI, and a FastAPI seller middleware, requires_payment.

Both sync and async usage are supported (see Sync and async).

Installation ​

Requires Python 3.10+.

bash
# Install canonical SDK package from PyPI
pip install open-agentpay

# Or install in editable mode for development from repository root
pip install -e sdk/python/packages/agentpay

The client ​

python
from agentpay import AgentPayClient, LocalSigner
from agentpay.policy import PolicyConfig, SQLitePolicyEngine

client = AgentPayClient(
    signer=LocalSigner(...),          # signs on-chain authorizations
    policy=SQLitePolicyEngine.create_in_memory(PolicyConfig(...)), # local financial firewall
    headers={...},                    # default headers, e.g. Authorization
    wallet_challenge_mode=True,        # price-check API-key wallet calls before retry
)
ArgumentRequiredPurpose
signeryesSigns EIP-712 / EIP-3009 authorizations for the on-chain path. In wallet mode no signature is created, so it can be a placeholder.
policyyesThe local policy engine. Evaluated before any payment. See Policy Configuration.
headersnoDefault request headers. Authorization: Bearer <api_key> authenticates the wallet request.
wallet_challenge_modenoSet True for AgentPay Gateway wallet calls. The SDK receives the 402 quote, evaluates local policy, then retries with PAYMENT-SIGNATURE. Defaults to False.

Because AgentPayClient extends httpx.Client, standard httpx options such as timeouts work as usual.

Choosing a payment mode ​

The mode is chosen by the credentials on the request. There is no automatic fallback between modes.

Wallet modeOn-chain mode
CredentialAPI key in Authorization headerLocal private key (LocalSigner)
Account neededYes: tenant, project, agent, key from the consoleNo
How it paysGateway returns an agentpay-wallet price challenge; SDK policy approves before wallet Hold → upstream → CaptureClient signs an EIP-3009 authorization; Facilitator settles on-chain
Latency / costInternal ledger, no gasNetwork confirmation, gas sponsored by the Facilitator
Best forFleets of agents inside one organizationCross-organization calls, no prior relationship

TIP

If a wallet-mode request has insufficient balance, you get 402 ERR_WALLET_INSUFFICIENT_BALANCE. The SDK does not retry on-chain. Switching modes is always an explicit decision in your code.

Price-aware wallet mode (API key) ​

Enable wallet_challenge_mode=True when using an AgentPay Gateway API key. The gateway's first response is a 402 with the exact route price; no wallet hold or upstream call happens yet. The SDK checks that quote against its local policy and reserves the local budget before retrying with a one-time PAYMENT-SIGNATURE wallet authorization. The gateway then consumes the challenge and performs the wallet Hold → upstream → Capture lifecycle.

This is an AgentPay-specific x402 scheme (agentpay-wallet), not EIP-3009. It does not invoke the signer or a Facilitator. The client constructor currently still requires a signer, but it is not used on this path.

python
import os

from agentpay import AgentPayClient, LocalSigner
from agentpay.policy import PolicyConfig, SQLitePolicyEngine

# Wallet mode makes no on-chain signature, so the signer is a placeholder.
# ⚠️ TESTNET DEVELOPMENT ONLY: This is a well-known public Hardhat key. NEVER deposit real funds!
dev_key = os.getenv("AGENT_PRIVATE_KEY", "0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80")
signer = LocalSigner(dev_key)

policy = SQLitePolicyEngine.create_in_memory(
    PolicyConfig(
        id="wallet_firewall",
        name="Wallet Firewall",
        wallet_address=signer.address,
        max_per_tx_base_units=100_000,         # 0.10 USD per request (wallet minor units)
        rolling_budget_24h_base_units=5_000_000, # 5.00 USD per rolling 24h
        whitelist_domains=frozenset(["gateway.example.com"]),
    )
)

client = AgentPayClient(
    signer=signer,
    policy=policy,
    headers={"Authorization": f"Bearer {os.environ['AGENTPAY_API_KEY']}"},
    wallet_challenge_mode=True,
)

resp = client.get("https://gateway.example.com/v1/market-data?ticker=NVDA")
print(resp.status_code, resp.json())

After local approval, the gateway authenticates the key, resolves tenant, project and agent from it, rechecks the server-side route price, consumes the challenge once, holds the price in the tenant wallet, calls the upstream with credentials the gateway holds, and captures the charge on 2xx. Your code never sees the upstream's secret.

An alternative to the Authorization header is X-API-Key. Wallet challenge mode is opt-in; without it, credential calls follow the SDK's configured unmetered_credential_policy and do not get this price-aware challenge handling.

On-chain mode (x402) ​

python
import os

from agentpay import AgentPayClient, LocalSigner
from agentpay.policy import PolicyConfig, SQLitePolicyEngine

signer = LocalSigner(private_key=os.environ["AGENT_PRIVATE_KEY"])
policy = SQLitePolicyEngine.create_in_memory(
    PolicyConfig(
        id="onchain_firewall",
        name="On-Chain Firewall",
        wallet_address=signer.address,
        max_per_tx_base_units=1_000_000,         # 1 USDC
        rolling_budget_24h_base_units=10_000_000, # 10 USDC
        whitelist_payees=frozenset(["0x70997970C51812dc3A010C7d01b50e0d17dc79C8"]),
    )
)

client = AgentPayClient(signer=signer, policy=policy)   # no API key needed

resp = client.get("https://gateway.example.com/v1/market-data")
print(resp.json())

When the server answers 402 with a PAYMENT-REQUIRED challenge, the client does this transparently:

text
1. Decode the challenge (price, payee, asset, network, expiry, scheme)
2. Policy: evaluate → atomically RESERVE budget (reject here = no authorization is sent)
3. Select by scheme: sign EIP-3009, or create an `agentpay-wallet` authorization without calling the signer
4. Replay the same request with the `PAYMENT-SIGNATURE` header
5. On success: COMMIT the local reservation; retain it on ambiguous timeout / `5xx`

Failure handling matters. After a signature has been sent, a timeout or 5xx does not release your budget, because the payment may still settle. The reservation is released only once the authorization has expired and is confirmed unspent. This is what prevents double charging.

Private keys

Load keys from environment variables or a secrets manager, never from source code or prompts. Never expose a signer or policy object to the model as a tool. For production, plan on KMS / HSM-backed signing (not yet available).

Sync and async ​

The client is synchronous by default. For async code, get an async client from the same object:

python
import asyncio

async def main():
    async with client.async_client() as aclient:
        resp = await aclient.get("https://gateway.example.com/v1/market-data")
        print(resp.status_code, resp.json())

asyncio.run(main())

Use async with so connections are closed properly.

Local financial firewall ​

The policy argument accepts SQLitePolicyEngine, which supports two storage modes:

ModeStateUse for
SQLitePolicyEngine.create_in_memory(...)In memory (:memory:, lost on restart)Tests, demos, short-lived agents
SQLitePolicyEngine(conn, config)Durable SQLite file, atomic reservation in an exclusive transactionLong-running agents, anything where budget must survive restarts
python
from agentpay.policy import PolicyConfig, SQLitePolicyEngine, WhitelistMode

# WhitelistMode.SIMPLE (default): empty whitelists allow all by default;
# WhitelistMode.STRICT: requires explicit network, asset, payee (and domain) whitelists.
policy = SQLitePolicyEngine.create_in_memory(
    PolicyConfig(
        id="agent_firewall",
        name="Agent Firewall",
        wallet_address=signer.address,
        max_per_tx_base_units=500_000,
        rolling_budget_24h_base_units=5_000_000,
        whitelist_mode=WhitelistMode.SIMPLE,
        whitelist_payees=frozenset(["0x742d35Cc6634C0532925a3b844Bc454e4438f44e"]),
    )
)

All amounts are integers in the smallest unit (USDC has 6 decimals, so 500_000 is 0.5 USDC). On the on-chain path, PolicyConfig supports two whitelist modes via whitelist_mode: WhitelistMode.SIMPLE (default, where empty whitelist dimensions allow requests through) and WhitelistMode.STRICT (where every whitelist dimension must be populated and matched). The engine is fail-closed: any error means the payment is rejected. See Policy Configuration for every rule.

One key, one ledger

A private key must map to exactly one SQLite ledger. Running several processes with the same key but separate ledgers multiplies your effective budget.

Agent identity and audit metadata ​

Identity comes from the credential, not from headers. The gateway derives agent_id from the API key. Any X-Agent-ID (or other X-Agent-*) header your client sends is stripped and ignored, so it cannot be used to impersonate another agent. You do not need to, and should not, set it.

What you can add is optional, self-reported context, used only to group calls in the console timeline:

HeaderPurpose
X-Session-IDGroup calls belonging to one workflow session
X-Task-IDGroup calls belonging to one task
X-Tool-NameName of the tool making the call
python
client = AgentPayClient(
    signer=signer,
    policy=policy,
    headers={
        "Authorization": f"Bearer {api_key}",
        "X-Session-ID": "session_nvda_analysis_001",
        "X-Task-ID": "task_market_data_fetch",
        "X-Tool-Name": "fetch_stock_quote",
    },
)

These headers are 100% optional and never affect authentication, billing or policy:

With the headersWithout them
Request handlingSanitized (allowed characters only, max 128 characters) and recordedTreated as empty; the request proceeds normally
Billing and limitsUnaffected; based only on the API key's agentUnaffected
Console timelineFilter and group by session / task; shown with a "self-reported" badgeEach call shown on its own, with the gateway-observed facts

The gateway records its own observed facts (status, latency, charge, policy decision) separately from anything self-reported, so the audit trail can always distinguish what was observed from what was declared.

Idempotency and safe retries ​

Networks fail, and the dangerous retry is the one that pays twice. Rules to follow:

  1. Send an Idempotency-Key for any request that costs money, and reuse the same key when you retry the same logical request.
  2. The same key with the same request replays the stored result (X-Cache: HIT) at no additional cost, including after an upstream 5xx (the original hold is reused).
  3. The same key with a different body returns 409 ERR_IDEMPOTENCY_CONFLICT. Keys are not reusable across different requests.
  4. A timeout is not a failure. If a request times out, the outcome is unknown. Retry with the same key rather than a new one.
python
import uuid

key = str(uuid.uuid4())          # one key per logical operation

resp = client.post(
    "https://gateway.example.com/v1/report",
    json={"ticker": "NVDA"},
    headers={"Idempotency-Key": key},
)
# On a timeout, call again with the SAME key:
# resp = client.post(..., headers={"Idempotency-Key": key})

Handling errors ​

A policy or payment rejection is not a crash: the request was refused before any money moved. Check the HTTP status and the canonical error code in the JSON body, not the message text.

python
resp = client.get("https://gateway.example.com/v1/market-data")

if resp.status_code == 200:
    data = resp.json()
elif resp.status_code == 402:
    # A 402 WITHOUT a PAYMENT-REQUIRED challenge is a terminal error
    # (for example insufficient wallet balance). Do not retry blindly.
    print("Payment refused:", resp.json())
elif resp.status_code in (403, 429):
    # Policy, route or rate-limit rejection
    print("Blocked by policy:", resp.json())
else:
    resp.raise_for_status()
CodeHTTPMeaningTypical handling
ERR_POLICY_MAX_PER_TX403Price above the per-transaction capDo not retry; investigate the price
ERR_POLICY_BUDGET_EXCEEDED403Rolling budget would be exceededStop; wait for the window or raise the budget
ERR_POLICY_CIRCUIT_BROKEN429Circuit breaker openFix the loop; retry after the cooldown
ERR_RATE_LIMIT_EXCEEDED429Too many requestsBack off
ERR_ROUTE_NOT_ALLOWED403Agent may not call this routeChange the allow-list, not the code
ERR_WALLET_INSUFFICIENT_BALANCE402Wallet balance too lowTop up; no automatic on-chain fallback
ERR_WALLET_FROZEN403Wallet frozenResolve in the console
ERR_API_KEY_INVALID401Unknown, revoked or expired keyCheck or rotate the key
ERR_AGENT_SUSPENDED / ERR_AGENT_REVOKED403Agent has been stoppedRe-enable or reissue
ERR_IDEMPOTENCY_CONFLICT409Same key, different requestUse a new key for a new operation
ERR_UPSTREAM_TIMEOUT / ERR_UPSTREAM_FAILED504 / 502Upstream problem; funds stay held for reviewRetry with the same idempotency key

LangChain and CrewAI paid tools ​

Wrap a function so each call to it is a governed, paid call:

python
from agentpay.integrations.langchain import paid_tool

@paid_tool(
    name="fetch_stock_quote",
    description="Fetch a real-time US stock quote (charged per call)",
    client=client,
)
def fetch_stock_quote(ticker: str) -> dict:
    resp = client.get(f"https://gateway.example.com/v1/market-data?ticker={ticker}")
    return resp.json()

result = fetch_stock_quote.invoke({"ticker": "NVDA"})

The tool only sees the function's inputs and outputs. The model can call the tool but has no access to the client's policy, signer or API key.

Seller side: FastAPI middleware ​

To charge for your own FastAPI endpoint:

python
from fastapi import FastAPI
from agentpay.fastapi import requires_payment

app = FastAPI()

@app.get("/v1/market-data")
@requires_payment(
    price=100_000,                                         # 0.1 USDC
    payee="0xSellerPayoutAddress...",
    asset="0x036CbD53842c5426634e7929541eC2318f3dCF7e",    # Base Sepolia USDC
    network="eip155:84532",
    facilitator_url="https://facilitator.agentpay.dev",
)
async def get_market_data():
    return {"status": "success", "data": "Alpha Market Data"}

Unpaid requests get a 402 with a PAYMENT-REQUIRED challenge; valid signed requests are verified with the Facilitator before your handler runs. To monetize an existing API without changing its code, put it behind the Gateway instead.

Testing locally ​

  • In-memory sandbox. The local embedded topology routes requests through an in-memory transport to the gateway code and a mock EVM RPC, with no sockets and no testnet funds. This is how make demo and the test suite run in seconds.
  • Against a local gateway. Follow the Quickstart to run the gateway and Postgres in Docker and call it with a development key.
  • Use rejection tests. A request blocked by policy creates no signature and no charge, so it is safe to test limits repeatedly.

httpx.ReadTimeoutThe outcome is unknown. Retry with the same idempotency key.
