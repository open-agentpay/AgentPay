5-Minute Quickstart ​

In this guide you will run the AgentPay gateway on your own machine, make a paid API call from a Python agent, and then see the firewall in action. No wallet, testnet funds or real money are required.

Sandbox only

AgentPay is experimental and has not been independently audited. Everything in this guide runs locally against development data. Never point it at mainnet funds.

What you will do ​

#StepTimeWhat you will see
1Get the code and start PostgreSQL~1 minA running database container
2Start the gateway~1 minHealth checks returning ok
3See the 402 Payment Required challenge~30 sThe raw x402 challenge from the gateway
4Install the Python SDK~1 minagentpay importable
5Make your first governed request~30 sA 200 response, paid from the tenant wallet
6Retry safely with an idempotency key~30 sA replayed response at zero extra cost
7Watch the firewall stop a runaway loop~1 minPayments approved, then blocked
8Clean up~10 sEverything stopped

Prerequisites ​

ToolVersionCheck with
Gitany recentgit --version
Docker + Compose v2Docker 24+docker compose version
Go1.21+go version

Make sure ports 5432 (PostgreSQL), 8080 (gateway data plane) and 8081 (admin API) are free. On Windows, use WSL 2.

1. Get the code and start PostgreSQL ​

bash
git clone https://github.com/open-agentpay/AgentPay.git
cd AgentPay

docker compose up -d postgres

Confirm the container is up and healthy:

bash
docker compose ps

You should see the postgres service with a status of running (or healthy). The schema is created from infra/postgres/schema.sql.

2. Start the gateway ​

Open a second terminal (the gateway runs in the foreground) and start it:

bash
cd AgentPay/services/gateway
go run ./cmd/gateway

The first run downloads Go modules and compiles, so it may take a minute. When it is ready it logs that it is listening:

PortPurpose
127.0.0.1:8080Data plane — the traffic your agents send
127.0.0.1:8081Admin API — used by the management console

Back in your first terminal, check that the gateway is alive:

bash
curl -s http://127.0.0.1:8080/healthz
curl -s http://127.0.0.1:8080/readyz
curl -s http://127.0.0.1:8080/version

/healthz means the process is up; /readyz means it has loaded its configuration and can serve requests; /version prints build metadata.

Where does the gateway get its routes?

On start it loads a configuration snapshot. The development configuration includes a sample paid route, /weather/current, which is the one used below. Gateways always report which snapshot served a request in the X-Config-Version response header. See Gateway Configuration to define your own routes.

3. See the 402 Payment Required challenge ​

Before using the SDK, look at what an agent sees when it calls a paid route without any credentials:

bash
curl -i "http://127.0.0.1:8080/weather/current?city=SanFrancisco"

Expected result:

text
HTTP/1.1 402 Payment Required
PAYMENT-REQUIRED: eyJ2ZXJzaW9uIjoiMi4wIiwi...

The PAYMENT-REQUIRED header is a Base64URL-encoded JSON challenge: price, payee, asset, network and an expiry. Decode it to read it:

bash
curl -si "http://127.0.0.1:8080/weather/current?city=SanFrancisco" \
  | grep -i '^payment-required:' | cut -d' ' -f2 | tr -d '\r' \
  | python3 -c "import sys,base64,json; s=sys.stdin.read().strip(); s+='='*(-len(s)%4); print(json.dumps(json.loads(base64.urlsafe_b64decode(s)),indent=2))"

You will see fields such as network, asset, amount (in the smallest unit — USDC has 6 decimals, so 100000 is 0.1 USDC), payee, validBefore and scheme. This unauthenticated request shows the on-chain path. The API-key wallet path also uses an x402-style 402 challenge: the gateway first quotes its price, the SDK checks it against local policy, then retries with a wallet authorization. It does not create an EIP-3009 signature or call a facilitator.

4. Install the Python SDK ​

From the repository root, in a virtual environment:

bash
python3 -m venv .venv
source .venv/bin/activate          # Windows (WSL): same; PowerShell: .venv\Scripts\Activate.ps1

pip install -e sdk/python/packages/agentpay
python -c "import agentpay; print('agentpay OK')"

5. Make your first governed request ​

Create first_request.py:

python
import os

from agentpay import AgentPayClient, LocalSigner
from agentpay.policy import PolicyConfig, SQLitePolicyEngine

# 1. Signer. In wallet mode no on-chain signature is made, so this is only a placeholder.
#    ⚠️ TESTNET DEVELOPMENT ONLY: This is a well-known public Hardhat key. NEVER deposit real funds!
dev_key = os.getenv("AGENT_PRIVATE_KEY", "0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80")
signer = LocalSigner(dev_key)

# 2. Local financial firewall: protects you from an agent looping and burning budget.
#    Amounts are integer minor units; the wallet challenge reports USD pricing.
policy = SQLitePolicyEngine.create_in_memory(
    PolicyConfig(
        id="quickstart_firewall",
        name="Quickstart Firewall",
        wallet_address=signer.address,
        max_per_tx_base_units=1_000_000,       # at most 1 USD per request
        rolling_budget_24h_base_units=10_000_000, # at most 10 USD per 24 hours
        whitelist_domains=frozenset(["127.0.0.1", "localhost"]),
    )
)

# 3. API key issued for your agent (development key seeded with a test wallet balance).
api_key = os.getenv("AGENTPAY_API_KEY", "apk_live_valid123")

# 4. Enable price-aware wallet mode. The SDK first receives a 402 quote, checks the
#    exact price against local policy, then authorizes and retries the request.
client = AgentPayClient(
    signer=signer,
    policy=policy,
    headers={"Authorization": f"Bearer {api_key}"},
    wallet_challenge_mode=True,
)

# The first request gets a price challenge. Only after local approval does the SDK
# retry; the gateway then holds the tenant-wallet amount and calls the upstream.
response = client.get("http://127.0.0.1:8080/weather/current?city=SanFrancisco")
print("Response status:", response.status_code)
print("Data:", response.json())

AgentPayClient extends httpx.Client, so get, post, timeouts and the rest of the httpx API work as usual. The main AgentPay options are:

ArgumentRole
policyThe local firewall (per-request cap, rolling budget, payee whitelist). In wallet challenge mode it evaluates the quoted price before the gateway places a hold.
signerSigns EIP-712 / EIP-3009 authorizations for the on-chain path. Wallet challenge mode does not invoke it, though the current client constructor still requires a signer.
headersDefault headers. Authorization: Bearer <api_key> authenticates the wallet request.
wallet_challenge_modeSet to True for AgentPay Gateway API-key wallet calls. The SDK waits for the gateway's price challenge, evaluates local policy, then retries with PAYMENT-SIGNATURE. Defaults to False.

If you configure allow-lists, wallet challenges use asset USD and a payee such as agentpay:route:<route-id>; on-chain challenges continue to use token addresses.

Prefer async? Use the async client from the same object:

python
import asyncio

async def main():
    async with client.async_client() as aclient:
        res = await aclient.get("http://127.0.0.1:8080/weather/current?city=SanFrancisco")
        print(res.status_code, res.json())

asyncio.run(main())

Run it:

bash
python first_request.py

Expected output:

text
Response status: 200
Data: {...weather data...}

That one call did a lot. In order, the gateway:

  1. Quoted the route price in a 402 agentpay-wallet challenge without placing a hold.
  2. Evaluated local policy against the exact quoted amount and reserved the SDK budget.
  3. Authorized the original request with PAYMENT-SIGNATURE; the gateway validates and consumes the one-time challenge.
  4. Held the route price in the tenant wallet, then forwarded the request with upstream credentials injected by the gateway.
  5. Captured the held amount after the upstream returned 2xx, appending an immutable ledger entry.

If the upstream had returned a 4xx, the hold would have been released and nothing charged. If it had returned a 5xx or timed out, the hold would stay in place and the payment would be marked for review. It is never auto-charged and never auto-released.

Sandbox key

apk_live_valid123 is a development seed key that only exists in the local development configuration. In a real deployment you create agents and keys in the Management Console; keys are shown once and stored only as hashes.

6. Retry safely with an idempotency key ​

Networks fail. The danger is a retry that charges twice. Send the same request twice with an Idempotency-Key:

bash
for i in 1 2; do
  curl -si "http://127.0.0.1:8080/weather/current?city=SanFrancisco" \
    -H "Authorization: Bearer apk_live_valid123" \
    -H "Idempotency-Key: quickstart-demo-001" \
    | grep -iE '^(HTTP/|x-cache|x-config-version)'
  echo "---"
done

Expected result:

text
HTTP/1.1 200 OK
X-Config-Version: <n>
---
HTTP/1.1 200 OK
X-Cache: HIT
X-Config-Version: <n>
---

The second response is replayed from the first (X-Cache: HIT) and costs nothing extra. Re-sending the same key with a different request body is rejected with 409 ERR_IDEMPOTENCY_CONFLICT, so a key can never be reused to smuggle in a different purchase.

7. Watch the firewall stop a runaway loop ​

The most important property of AgentPay is that a misbehaving agent gets cut off. The repository ships a one-command demo that shows three scenarios: a normal payment succeeds, an over-limit payment is refused, and a repeating payment loop trips the circuit breaker.

From the repository root:

bash
make demo

The demo can run against a local mock chain (no wallet or testnet funds needed) or against Arbitrum Sepolia; see the repository README for how to switch. Look for these three outcomes in the output:

ScenarioExpected outcome
Normal call within limitsApproved and paid
Single payment above the per-transaction capRefused — nothing is signed or charged
Same payment repeated in a tight loopApproved at first, then circuit breaker opens and further payments are blocked

To set your own limits, see Policy Configuration.

8. Clean up ​

Stop the gateway with Ctrl+C in its terminal, then:

bash
docker compose down          # stop PostgreSQL (data is kept in its volume)
docker compose down -v       # …or also delete the data for a fully clean slate

What just happened ​

text
                    ┌─ wallet path (steps 5–6) ─┐
Agent ── API key ──▶│  402 quote → SDK policy → │──▶ Upstream API
                    │  authorize → HOLD → CAPTURE│
                    └────────────┬──────────────┘
                                 ▼
                       PostgreSQL ledger + audit trail

Agent ── no key ───▶ Gateway ──▶ 402 + PAYMENT-REQUIRED   (on-chain path, step 3)
  • Agents authenticate with a revocable API key. They never hold a private key on the wallet path.
  • In SDK wallet challenge mode, the quoted price is checked by the local policy before the gateway places a wallet hold. Enable it with wallet_challenge_mode=True.
  • Every charge goes through Hold → (fulfil) → Capture or Release, so you are only billed for successful deliveries.
  • Retries are made safe by idempotency keys.
  • Spending limits and the circuit breaker are enforced outside the model, so a prompt cannot talk its way past them.

Troubleshooting ​

SymptomLikely cause and fix
port is already allocated on docker compose upSomething else is using 5432. Stop it, or change the published port in docker-compose.yml.
Gateway exits with a database connection errorPostgreSQL is not ready yet. Wait a few seconds, check docker compose ps, then restart the gateway.
bind: address already in use on 8080 / 8081Another process holds the port. Find it with lsof -i :8080 and stop it.
go: go.mod requires go >= …Your Go version is too old. Upgrade to Go 1.21 or newer.
curl: (7) Failed to connectThe gateway is not running. Check the terminal where you ran go run ./cmd/gateway.
Python raises ConnectErrorWrong gateway_url, or the gateway is still compiling on first run.
401 ERR_API_KEY_INVALIDThe key is not known to the gateway. Use the seeded development key, or create one in the console.
402 ERR_WALLET_INSUFFICIENT_BALANCEThe wallet lacks funds for the route price. The gateway will not fall back to on-chain payment. Top up the wallet in the console.
403 ERR_POLICY_MAX_PER_TX / ERR_POLICY_BUDGET_EXCEEDEDThe firewall did its job. Raise the limits in your policy if the request is legitimate.
pip install fails on Python 3.9 or olderUse Python 3.10+.

If you are still stuck, open an issue with the gateway log and the output of curl -i for the failing request.
