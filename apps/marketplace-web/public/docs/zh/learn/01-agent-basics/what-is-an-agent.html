什么是 AI Agent？ ​

一、从聊天到执行任务 ​

我们平时使用 AI，最常见的方式是提问，然后等待回答。

例如：

帮我分析一下最近的 AI 行业动态。

普通的大模型应用可以根据已有知识生成分析。如果没有接入搜索工具，它可能无法获取最新的信息。

现在，我们把任务换成：

搜索最近一周的 AI 行业新闻，筛选出最值得关注的 5 条，阅读原文，比较不同来源的观点，最后生成一份简报。

要完成这个任务，系统可能需要：

  1. 搜索相关新闻。
  2. 获取网页内容。
  3. 判断信息是否相关。
  4. 比较不同来源的观点。
  5. 发现信息不足时继续搜索。
  6. 整理结果并生成简报。

这已经不只是生成一段文字，而是一个包含多个步骤的任务执行过程。

AI Agent 的核心特征，是围绕目标，结合模型判断、工具调用和执行反馈，完成一系列任务。

二、LLM、工作流与 Agent 有什么区别？ ​

1. LLM：负责理解与生成 ​

LLM（Large Language Model，大语言模型）能够理解输入、生成文本、分析信息，并根据上下文提出建议。

例如：

text
用户提问
   ↓
大语言模型
   ↓
生成回答

模型可以解释如何查询天气，但如果没有连接天气服务，就不一定能够获取实时天气。

它可以生成 SQL 语句，但不代表已经连接数据库并执行了查询。

因此，需要区分两件事：

  • 知道怎么做：模型生成了方法或操作建议。
  • 实际做了什么：程序执行了操作，并获得了结果。

2. 工作流：按照预定步骤执行 ​

工作流（Workflow）按照预先定义的规则执行任务。

例如：

text
读取文章
   ↓
提取正文
   ↓
生成摘要
   ↓
保存到数据库
   ↓
发送通知

每一步的执行顺序主要由程序决定。

工作流的优点是结构清晰、容易测试、执行过程相对可预测。

如果任务步骤固定，通常没有必要为了使用 AI 而引入复杂的 Agent。

3. Agent：根据任务和反馈决定下一步 ​

Agent 通常会让模型参与下一步行动的选择。

例如：

text
接收研究任务
     ↓
分析任务目标
     ↓
调用搜索工具
     ↓
获取搜索结果
     ↓
判断信息是否充分
   ┌─┴─────┐
   │       │
 不充分   已充分
   │       │
继续搜索  生成报告

Agent 可以根据实际执行结果调整后续行动，而不是只能沿着一条固定路径执行。

不过，Agent 并不一定比工作流更好。

如果任务简单、步骤固定，使用普通程序或工作流往往更可靠、更便宜，也更容易调试。

三者对比 ​

维度LLM 应用工作流Agent
核心能力理解与生成按规则执行步骤根据目标选择行动
步骤安排通常以单次调用为主主要由程序预先定义可以根据结果动态调整
工具调用可以支持可以支持通常用于完成任务
执行循环通常较少由流程定义可以根据反馈反复执行
可预测性取决于模型与任务通常较高受模型决策与环境影响
适用场景问答、总结、改写固定业务流程需要动态决策的多步骤任务

这些分类不是绝对的。一个系统可以同时包含 LLM、工作流和 Agent。

三、Agent 的基本组成 ​

一个常见的 Agent 系统，可以抽象为以下几个部分。

1. 模型（Model） ​

负责理解任务、分析上下文、选择工具，以及根据执行结果决定下一步。

模型本身不会自动获得操作系统、数据库或网络的访问权限。这些能力需要由外部程序提供。

2. 指令与目标（Instructions / Goal） ​

告诉 Agent 要完成什么、遵守哪些约束，以及什么样的结果才算完成。

例如：

text
目标：生成一份 AI 行业日报。

约束：
- 优先使用最近 24 小时的信息。
- 尽量核对多个独立来源。
- 无法确认的信息必须标记。
- 最多执行 10 次工具调用。
- 最终输出 5 条重点新闻。

明确目标和约束，可以减少任务偏离和无效调用。

3. 工具（Tools） ​

为 Agent 提供与外部世界交互的能力。

常见工具包括：

  • 搜索引擎。
  • HTTP API。
  • 数据库查询。
  • 文件读取与写入。
  • 代码执行环境。
  • 业务系统接口。
  • 其他 Agent 提供的服务。

工具调用的原理将在下一篇详细介绍。

4. 上下文与记忆（Context / Memory） ​

帮助 Agent 利用当前任务信息和历史结果。

例如：

  • 当前任务的目标。
  • 已经搜索过的新闻。
  • 已经调用过的工具。
  • 前几步执行的结果。
  • 用户明确提供的偏好。

需要注意，上下文不等于长期记忆。

对话中保留的信息、数据库中的历史记录和独立的记忆系统，是不同的实现方式。

5. 执行循环（Execution Loop） ​

负责把模型决策、工具执行和结果反馈串联起来。

text
接收任务
   ↓
构造模型输入
   ↓
模型决定下一步
   ↓
是否需要调用工具？
   ├── 是 → 检查权限 → 执行工具 → 返回结果
   │                          ↑          │
   │                          └──────────┘
   │
   └── 否 → 输出最终结果

实际工程中，还需要设置最大迭代次数、超时、错误处理和人工介入条件。

四、一个完整的 Agent 示例 ​

假设用户提出任务：

帮我比较三家公司的公开产品信息，整理一份简短的对比报告。

Agent 可能按以下步骤执行：

  1. 分析任务，确定需要比较的公司和维度。
  2. 调用搜索工具，获取公开资料。
  3. 调用网页读取工具，获取具体产品信息。
  4. 检查资料是否完整，以及不同来源之间是否存在冲突。
  5. 必要时再次搜索。
  6. 对信息进行归纳。
  7. 生成对比报告，并注明信息来源。

整个过程中的职责分工如下：

参与者职责
用户提出目标和约束
LLM理解任务、提出行动建议、整理结果
Agent 程序控制执行流程、调度工具、管理状态
工具执行搜索、读取网页等具体操作
外部服务返回实际数据或执行结果

这里最重要的一点是：

模型提出行动建议，程序决定如何执行，工具返回实际结果。

五、Agent 不是什么？ ​

误区 1：接入大模型就是 Agent ​

不一定。

一个只调用模型生成文本的应用，可以是普通 LLM 应用。

Agent 通常还包含目标驱动的行动选择、工具执行与结果反馈。

误区 2：Agent 一定需要复杂框架 ​

不需要。

一个简单的 Agent 可以由普通 Python 或 Java 程序实现。

框架的价值主要在于减少重复开发、提供标准抽象，以及帮助组织更复杂的执行流程。

误区 3：Agent 越自主越好 ​

不一定。

如果任务涉及删除数据、发送消息、修改生产环境或使用真实资金，完全自主执行可能带来严重后果。

自主度应该与任务风险、可逆性和授权范围相匹配。

误区 4：Agent 能完成任务，就代表结果正确 ​

不成立。

Agent 可能使用过时数据、调用错误工具、误解工具结果，甚至在失败后错误地报告任务成功。

因此，重要任务需要结果校验、日志记录和失败恢复机制。

六、什么时候应该使用 Agent？ ​

可以参考以下判断。

适合考虑 Agent 的场景：

  • 任务需要根据中间结果动态决定下一步。
  • 任务需要组合多个不同的工具。
  • 输入与执行路径存在较大变化。
  • 可以定义明确的完成条件与执行边界。
  • 能够验证结果，并承担合理的执行成本。

不一定需要 Agent 的场景：

  • 只有一次简单问答。
  • 任务步骤固定且规则明确。
  • 对结果确定性要求很高。
  • 调用模型带来的成本明显高于实际收益。
  • 系统无法安全地限制工具权限。

工程实践中，可以先用确定性的工作流解决问题，再在确实需要动态决策的环节引入 Agent。

七、小结 ​

理解 Agent，可以记住下面这句话：

LLM 负责理解与生成，工具负责执行具体操作，Agent 程序负责把目标、决策、行动和反馈组织起来。

Agent 的价值不只是让 AI 回答得更好，而是让 AI 能够在实际环境中完成多步骤任务。

但一旦系统开始执行真实操作，就必须同时考虑权限、成本、错误处理和安全边界。
