支付策略引擎：如何限制 Agent 的消费 ​

一、为什么需要支付策略引擎？ ​

假设你给一个研究 Agent 提供了 10 USDC 的预算，让它自动购买数据服务。

它可能正常调用 API，也可能因为模型误判、任务循环或恶意输入，反复购买不必要的数据。

如果系统只提供钱包和支付接口，那么只要 Agent 能够发起有效支付，就可能持续消费。

支付策略引擎（Spending Policy Engine）就是为了在支付执行之前，对请求进行独立的规则检查。

可以把它理解为银行账户的消费规则与 API 网关的访问控制相结合的一层系统。

二、支付策略引擎的基本流程 ​

text
Agent 提出支付请求
        ↓
验证 Agent 身份
        ↓
检查服务商
        ↓
检查单笔金额
        ↓
检查预算
        ↓
检查调用频率
        ↓
检查风险与审批要求
        ↓
允许 / 拒绝 / 等待审批

这里的“允许”意味着请求通过了策略检查，并不等于资金已经完成结算。

后续仍需要执行授权、支付、交付和状态更新等流程。

三、第一类规则：单笔支付限额 ​

单笔限额用于限制一次请求最多可以花多少钱。

例如：

yaml
policy:
  max_transaction_amount: 0.10

假设金额单位为 USDC。

那么：

text
请求 A：0.05 USDC → 允许继续检查
请求 B：0.10 USDC → 允许继续检查
请求 C：0.20 USDC → 拒绝

注意，前两个请求只是通过单笔限额检查，还需要满足其他规则。

单笔限额也不能代替预算限制。即使每次只花 0.01 USDC，连续调用很多次仍然可能产生较高成本。

四、第二类规则：时间窗口预算 ​

时间窗口预算用于限制一定时间范围内的累计消费。

例如：

yaml
budget:
  daily: 2.00

这里的 daily 需要在实际系统中明确是自然日预算还是滚动 24 小时预算。

假设采用滚动 24 小时预算，Agent 当前已经使用 1.80 USDC，剩余 0.20 USDC。

此时：

text
请求 A：0.05 USDC → 预算允许
请求 B：0.25 USDC → 预算不足

真实实现需要明确预算统计范围、时区、过期记录和并发处理规则。

对于 AgentPay MVP，研发计划采用滚动 24 小时预算，并计划使用 SQLite 事务实现原子预留。

五、第三类规则：商户白名单 ​

商户白名单用于限定 Agent 可以向哪些服务商付款。

例如：

yaml
allowed_merchants:
  - search-api
  - market-data
  - translation-api

如果 Agent 请求向 unknown-service 付款，即使金额只有 0.001 USDC，也应该因为服务商不在允许范围内而被拒绝。

白名单中的名称还必须与可信的服务身份建立可靠映射。

不能只相信服务端在请求中随意提供的一个名称，就把它当成可信商户身份。

在实际系统中，需要根据具体协议设计对收款方、服务标识和支付要求的验证方式。

六、第四类规则：调用频率限制 ​

频率限制用于控制单位时间内的请求数量。

例如：

yaml
limits:
  requests_per_minute: 10

假设 Agent 每分钟最多允许发起 10 次付费请求。

这有助于限制：

  • 无限调用循环。
  • 重复请求。
  • 异常高频消费。
  • 某些滥用行为。

但频率限制不等于预算限制。

如果每次请求费用不同，单纯限制请求数量并不能准确限制总消费。

因此，频率限制应与单笔限额、累计预算共同使用。

七、第五类规则：生命周期总额 ​

生命周期限额用于限制某个 Agent 在整个授权周期内可以使用的累计金额。

例如：

yaml
budget:
  lifetime: 20.00

假设某个 Agent 从创建至今累计消费了 19.90 USDC。

即使它今天的预算仍然充足，新的 0.20 USDC 请求也应该因为超过生命周期限额而被拒绝。

实际系统需要定义累计消费是否包括失败请求、退款和预留中的金额，并明确如何处理额度恢复。

八、第六类规则：人工审批 ​

并不是所有支付请求都适合自动通过。

例如：

yaml
approval:
  required_above: 1.00

这里表示超过 1 USDC 的请求需要进入审批流程，具体字段语义需要由系统定义。

审批可以采用这样的流程：

text
Agent 请求支付
      ↓
策略检查
      ↓
金额超过审批阈值
      ↓
进入待审批状态
      ↓
人工确认
      ↓
重新验证授权与支付参数
      ↓
继续执行

需要注意，审批结果必须绑定具体请求和参数。

如果审批后金额、收款方或其他关键字段发生变化，就不能直接沿用原来的审批结果。

九、预算预留：为什么必须先锁定额度？ ​

这是支付策略引擎中一个重要的工程问题。

假设剩余预算为 1 USDC，两个请求同时申请 0.70 USDC。

如果系统只检查余额而不预留额度，就可能同时批准两个请求。

因此，预算控制应当采用类似以下流程：

text
检查可用预算
      ↓
原子预留额度
      ↓
执行支付流程
      ↓
根据最终结果更新预算

可以把预算分为三个概念：

  • available：可用预算。
  • reserved：已经为待处理请求预留的预算。
  • spent：已确认消耗的预算。

在一个简单模型中：

[ available = limit - spent - reserved ]

例如：

text
总预算：10.00
已消耗：3.00
已预留：2.00

可用预算：5.00

如果新的请求需要 6.00，就不能再批准。

实际系统还需要定义预留过期、失败释放、未知支付状态以及退款等场景的处理规则。

对于结果未知的支付请求，不能仅因为超时就直接释放预算。 否则系统可能在第一次支付已经成功的情况下，又批准新的消费，突破原有预算约束。

十、策略引擎如何处理异常？ ​

一个实用的策略引擎至少需要区分以下结果：

结果含义后续动作
ALLOW请求满足策略条件进入后续授权与支付流程
DENY请求违反策略拒绝执行并记录原因
REQUIRE_APPROVAL需要人工审批进入审批流程
TEMPORARY_FAILURE暂时无法完成策略判断按明确规则等待、重试或拒绝
CIRCUIT_OPEN熔断器已打开暂停相关请求

这些状态是便于理解的设计示例，不是某个协议规定的固定枚举。

策略判断本身发生异常时，不应默认放行。

对资金相关操作，通常应采用失败关闭（Fail Closed）的思路：无法确认请求满足必要的安全条件时，不继续执行支付。

十一、熔断器：防止 Agent 失控消费 ​

假设一个 Agent 因为循环错误，连续向同一个服务发起请求。

系统可以综合以下信号：

  • 同一 Agent 的请求频率。
  • 同一资源的重复调用次数。
  • 连续失败次数。
  • 一段时间内的消费金额。
  • 是否出现异常重试行为。

达到规则阈值后，熔断器可以阻断相关支付请求。

例如：

text
Agent 连续触发异常
        ↓
达到熔断阈值
        ↓
CIRCUIT OPEN
        ↓
拒绝新的付费请求
        ↓
等待检查或恢复条件

熔断器不能只靠模型自行决定何时停止。

它应该由应用程序独立执行，并具备明确的触发条件和恢复规则。

十二、AgentPay MVP 应该先实现哪些策略？ ​

结合项目年底研发计划，建议优先实现以下最小集合：

  1. 单笔支付上限。
  2. 商户白名单。
  3. 生命周期限额。
  4. 滚动 24 小时预算。
  5. 基于原子预留的并发预算控制。
  6. 调用频率限制。
  7. 基础熔断机制。

更复杂的风险评分、动态定价、复杂审批工作流可以放到后续阶段。

原因很简单：先把确定性规则做对，比一开始就引入复杂的 AI 风险评分更容易验证，也更容易测试。

十三、小结 ​

支付策略引擎的任务不是判断 Agent 的所有决策是否聪明，而是确定一个支付请求是否满足预先设定的规则。

它至少需要控制：

  • 单笔金额。
  • 累计预算。
  • 服务商范围。
  • 调用频率。
  • 生命周期额度。
  • 审批条件。
  • 异常与熔断。

其中，预算预留、并发安全和异常状态处理尤其重要。

策略引擎的价值，在于让 Agent 的消费行为受到独立、明确、可测试的程序规则约束。
