支付状态机、幂等与故障恢复 ​

一、为什么支付系统不能只记录成功和失败？ ​

假设 Agent 购买一份数据，支付金额为 0.10 USDC。

客户端发送支付请求后，网络突然中断。

此时系统知道的事实只有：

我没有收到完整响应。

但它并不知道：

  • 请求是否到达了服务端。
  • 支付是否已经被验证。
  • 交易是否已经提交。
  • 交易是否已经确认。
  • 数据是否已经交付。

如果数据库只有一个字段：

text
status = SUCCESS / FAILED

就无法准确表示这些中间状态。

因此，支付系统需要使用状态机管理业务进度。

二、什么是状态机？ ​

状态机（State Machine）是一种用明确状态和允许的状态转换来管理流程的方法。

例如，一个支付请求可以经历：

text
CREATED
   ↓
AUTHORIZED
   ↓
VERIFIED
   ↓
COMPLETED

如果请求被拒绝，则可能进入：

text
REJECTED

如果请求过期，则可能进入：

text
EXPIRED

这里的状态名称只是一个简化示例。实际系统必须明确定义每个状态的含义、进入条件、允许的后续状态以及失败处理方式。

状态机的价值在于：系统不会因为收到一个错误响应，就随意把状态改成任意值。

三、AgentPay 为什么要拆分三类状态？ ​

AgentPay 的设计将支付意图、结算和服务交付分开管理。

1. Payment Intent：支付意图 ​

表示某个支付请求的业务生命周期。

示例状态：

text
CREATED
   ↓
AUTHORIZED
   ↓
VERIFIED
   ↓
COMPLETED

还可能存在：

text
REJECTED
EXPIRED
CANCELLED

需要注意，COMPLETED 在实际实现中应有明确语义，不能含糊地同时表示“已经授权”“已经交付”和“已经结算”。

2. Settlement：结算状态 ​

记录资金结算的进展。

text
NOT_STARTED
   ↓
SUBMITTED
   ↓
PENDING
   ├── CONFIRMED
   ├── FAILED
   ├── REORGED
   └── UNKNOWN

其中：

  • SUBMITTED：结算请求或交易已经提交。
  • PENDING：结果仍在等待确认。
  • CONFIRMED：达到系统定义的确认条件。
  • FAILED：有充分证据表明结算失败。
  • REORGED：已确认的交易受到链重组影响，需要重新核验。
  • UNKNOWN：暂时无法确定结果。

这些状态是 AgentPay 设计中的概念模型，实际状态转换应根据底层支付方案细化。

3. Fulfillment：服务交付状态 ​

记录购买的资源是否交付。

text
NOT_STARTED
   ↓
PROCESSING
   ├── DELIVERED
   ├── FAILED
   └── RECOVERY_REQUIRED

例如，数据已经查询成功并返回给客户端，可以标记为 DELIVERED。

如果支付流程已经进行，但上游 API 发生故障，就可能进入 RECOVERY_REQUIRED。

四、为什么要把三类状态分开？ ​

考虑以下场景：

text
支付授权成功
      ↓
结算已经确认
      ↓
上游数据服务超时
      ↓
Agent 没有拿到数据

此时：

text
Payment Intent：已授权或已完成相关授权步骤
Settlement：已确认
Fulfillment：需要恢复

如果系统把整个过程简单标记为 FAILED，就可能让重试逻辑误以为需要重新付款。

但实际上，资金可能已经成功转移。

正确做法是只恢复尚未完成的环节，而不是盲目重放整个支付流程。

五、什么是幂等？ ​

幂等（Idempotency）指在相同业务请求被重复提交时，系统能够避免重复产生不应该重复发生的业务效果。

例如，一个 Agent 发起支付请求：

text
支付 0.10 USDC

客户端等待超时后重新发送同一个业务请求。

如果系统没有幂等控制，就可能执行两次：

text
第一次：支付 0.10 USDC
第二次：支付 0.10 USDC

总计：0.20 USDC

如果两次请求本来代表同一笔业务，就产生了重复支付。

幂等机制的目标，是识别这两次请求属于同一个业务意图，并根据原请求的状态返回结果、继续处理或拒绝重复执行。

六、什么是幂等键？ ​

幂等键（Idempotency Key）是用于标识一次业务请求的唯一标识。

例如：

text
tenant_id = tenant-001
agent_id = research-agent
payment_intent_id = intent-123

可以为同一个支付意图生成稳定的幂等键。

一个简化的数据表设计如下：

sql
CREATE TABLE payment_intent (
    id TEXT PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    amount TEXT NOT NULL,
    status TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,

    UNIQUE (tenant_id, idempotency_key)
);

这是一个用于讲解唯一约束的 SQLite 示例，尚不是完整的生产级支付表结构。

唯一约束可以阻止同一租户下出现重复的幂等键记录。

但是，数据库唯一约束本身不能保证链上只发生一次支付。

系统仍然需要把幂等记录、状态机、外部支付调用和恢复流程正确结合起来。

七、为什么不能把每次 HTTP 请求都当成一笔新支付？ ​

假设 Agent 请求一个付费 API。

第一次请求超时后，HTTP 客户端自动重试。

如果每次 HTTP 请求都创建一个新的支付意图，系统就可能把同一笔业务拆成多个支付请求。

更合理的做法是：

text
一次业务支付意图
       ↓
稳定的 payment_intent_id
       ↓
稳定的幂等键
       ↓
允许多次安全查询或恢复

重试时应复用同一个业务意图标识，而不是随意生成新的支付标识。

对于不同层次的重试，还应区分：

  • 查询原请求状态。
  • 重试网络请求。
  • 重试上游服务调用。
  • 重新提交结算。
  • 创建全新的支付请求。

这些操作的风险和语义并不相同。

八、支付结果未知时怎么办？ ​

这是最重要的故障恢复场景之一。

假设系统提交了一笔结算请求，然后网络超时。

错误处理：

text
请求超时
   ↓
直接认定失败
   ↓
创建新支付

更合理的处理方式：

text
请求超时
   ↓
记录 UNKNOWN
   ↓
保留原支付意图与幂等键
   ↓
查询原请求状态
   ↓
根据结果恢复

如果原支付已经成功，系统就不应该再次发起一笔新的支付。

如果原支付尚未执行，需要根据底层服务的幂等能力和状态查询结果决定是否继续。

如果无法确认结果，则应保留未知状态，并采用明确的恢复或人工介入策略。

九、预算预留与幂等如何配合？ ​

假设 Agent 的预算为 1 USDC，申请支付 0.20 USDC。

系统首先为请求预留 0.20 USDC。

text
创建支付意图
      ↓
原子预留 0.20
      ↓
执行支付
      ↓
根据结果更新状态

不同结果对应不同处理。

场景 A：策略拒绝 ​

支付没有进入执行阶段。

系统可以拒绝请求，并确保没有残留预算预留。

场景 B：确认没有执行支付 ​

在能够可靠确认未发生支付的前提下，可以按规则释放预留。

场景 C：支付已确认成功 ​

系统将预留额度转换为已消耗额度。

场景 D：支付结果未知 ​

系统应保留足够的状态信息，避免因过早释放预算而重复授权新的消费。

这里的具体预算账务规则需要在实现中明确定义。

十、恢复机制应该做什么？ ​

一个 reconcile() 恢复流程可以定期或按需检查未完成的记录。

例如：

text
扫描未完成的支付记录
        ↓
读取当前状态
        ↓
查询支付或结算结果
        ↓
核对服务交付结果
        ↓
执行允许的状态转换
        ↓
更新数据库

需要遵守几个原则：

  1. 恢复过程必须可以重复执行。
  2. 不能把未知状态直接当成失败。
  3. 不能因为恢复任务重复运行就重复扣款。
  4. 状态转换必须经过校验。
  5. 无法自动判断的情况应保留记录并进入人工处理或专门恢复流程。

十一、AgentPay MVP 的最小实现范围 ​

结合项目研发计划，MVP 需要重点完成：

  • SQLite 持久化。
  • 支付意图、结算和交付的独立状态管理。
  • 状态转换守卫。
  • 稳定的幂等键。
  • 预算预留、提交和释放。
  • 网络超时后的状态核验。
  • 重复请求测试。
  • 进程中途崩溃后的恢复测试。

其中，故障注入测试非常重要。

例如，在不同执行阶段人为中断程序，检查重启后能否根据持久化状态继续处理，并验证不会因为重试产生重复结算。

十二、小结 ​

状态机负责管理支付流程走到了哪一步。

幂等负责识别重复业务请求。

恢复机制负责在超时、崩溃和外部服务故障后，安全地继续未完成的工作。

三者相互配合，才能降低重复扣款和状态错乱的风险。

需要牢记：

网络超时不等于支付失败，支付成功不等于服务交付成功，重复请求也不应该自动变成新的支付。
