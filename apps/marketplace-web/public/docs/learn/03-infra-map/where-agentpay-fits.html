Where AgentPay Fits ​

Experimental Project

AgentPay has not undergone an independent security audit. Do not use it with real production funds.

In a nutshell ​

AgentPay is the financial-control layer between an agent and funds: it decides whether to allow payment before it happens and makes failures recoverable and activity traceable afterward. It is not an agent framework, a payment protocol, or a blockchain.

What it does ​

Returning to the diagram in Agent Infrastructure Layers, AgentPay covers financial control and extends slightly into the adjacent layers:

CapabilityDescription
Pre-payment policy evaluationPer-transaction caps, rolling budgets, recipient and network allowlists, rate circuit breakers, and loop detection
Atomic budget reservationPrevents concurrent requests from exceeding the budget (see Budget Reservation)
Failure and unknown-result handlingTracks payment, settlement, and fulfillment separately; avoids blind retries when the outcome is unknown (see Timeout Is Not Failure)
Two payment railsOn-chain payments (x402) and a platform virtual wallet; insufficient balance does not silently switch to the other rail
Seller payment gatewayTurns an existing API into a pay-per-request endpoint without changing its business code
Tenant and agent managementTenant, project, and member permissions; agent and API key lifecycles; one-click disablement
Audit and reconciliationRecords requests, payments, settlement, fulfillment, and policy decisions for review by agent and session

What it does not do ​

Clear boundaries are as important as clear capabilities:

Not responsible forReason and guidance
Agent reasoning and orchestrationThese belong to models and frameworks such as LangChain or CrewAI. AgentPay integrates as a tool wrapper.
Defining the payment protocolThe on-chain path follows x402 V2. AgentPay uses the protocol; it does not define it (see AgentPay vs. x402).
Judging whether a service is valuableA firewall cannot tell that an allowlisted service returned a useless answer after being paid within budget.
Custody of your private keyOn the on-chain path, the key stays with the buyer; the gateway and clearing service do not handle it.
Withdrawals and transfersThe current platform virtual wallet is for closed-loop spending; it does not support withdrawals or transfers between users.
Operating a public clearing networkThe project provides a reference implementation, not a public clearing service.
Surviving a compromised hostIf the execution environment is fully compromised, a local private key may be exposed. Stronger isolation is planned for the future.

Three roles, three ways to use it ​

Buyer: safely call paid services from an agent ​

You build an agent that needs paid APIs but should not have unlimited spending authority.

  • Use the Python SDK and configure policy on the client.
  • To the agent, this is an ordinary HTTP call; when a payment requirement appears, the firewall evaluates it and the signer handles authorization.
  • Wrap the client as a paid tool for frameworks such as LangChain.

The smallest setup does not require deploying a service; the SDK and local firewall are enough.

Seller: turn an API into a paid endpoint ​

You provide an API and want to charge per request without changing its existing code.

  • Deploy the AgentPay Gateway as a proxy in front of the upstream service.
  • Configure routes, prices, payment methods, and recipient addresses in the gateway.
  • The gateway issues payment requirements, verifies payment, forwards requests, and avoids duplicate charges when the upstream service fails.

The gateway keeps the upstream service's real credentials; they are not exposed to callers.

Administrator: manage multiple agents and their funds ​

Your team or enterprise needs to manage many agents and a shared budget.

  • Use the Web Console to configure routes and policies, edit drafts, validate and publish them, and roll back if needed.
  • Manage tenants, projects, members, and API keys; assign each agent its own budget and limits.
  • Use audit timelines to inspect what each agent did, how much it spent, and why a request was allowed or rejected.
  • Disable an agent with one action if its behavior becomes abnormal.

Components ​

ComponentPurposeUsers
Python SDKClient interceptor, local policy engine, signerBuyers
Go GatewayReverse proxy, payment requirements and verification, wallet debits, idempotency and recoverySellers and administrators
Web ConsoleRoute and policy configuration, publish and rollback, wallets, agents, and auditAdministrators
Clearing service (reference implementation)Validates signatures and submits on-chain settlement; includes a local simulationDevelopment and demos
Specifications and test vectorsAuthoritative definitions for protocol, state machine, error codes, and audit eventsIntegrators and developers building extensions

AgentPay can run in two forms:

  • Embedded local mode: all components run in one process without networking, suitable for development, testing, and demos (make demo uses this form).
  • Distributed mode: the buyer runs in its own environment while the gateway and clearing service run in the cloud and communicate over HTTPS, matching a typical deployment.

FAQ ​

Q: I only want to stop my agent from overspending. Do I need to deploy the gateway? No. The local SDK firewall can already enforce per-transaction limits, budgets, request rates, and allowlists. Use the gateway and console when you need centralized management, paid API access, or platform wallets.

Q: Is AgentPay a wallet product? No. The on-chain path uses the buyer's own wallet and private key. The platform virtual wallet is an internal gateway ledger account for low-cost, low-latency small charges; it is not a public wallet application.

Q: Can it work with my existing agent framework? Yes. AgentPay integrates through HTTP client interceptors and tool wrappers; you do not need to change frameworks.
